# ใบสั่งงาน — ส่ง "แบบหน้าจอ" มาแทนโค้ด แล้ว C ประกอบลงแอปจริง (8 ก.ย. 2569)

**จากเจ้าของ ผ่าน C (ฝั่งหลังบ้าน) ถึง GPT** · ไฟล์นี้แทนลำดับงานในหัวข้อ ฏ ของ `2026-09-08-proposal-one-inbox-ai-secretary.md`
เรื่องอื่นในไฟล์นั้น (การ์ด 12 ชนิด · หน้าจอ 9→3 · รายการฆ่าทิ้ง) **ยังใช้เหมือนเดิมทุกข้อ**

## 1. เปลี่ยนอะไร

เจ้าของสั่งเปลี่ยนวิธีส่งของ:

| เดิม | ใหม่ |
|---|---|
| GPT สร้างแอป SwiftUI ใน workspace ส่วนตัว แล้วส่งรายงานความคืบหน้ามา | **GPT ส่ง "แบบหน้าจอ" (สเปก + ภาพ) มาที่ `from-gpt/`** |
| C ตรวจรายงาน แล้วรอของ | **C ประกอบแบบนั้นลงแอปจริงที่ทีมใช้อยู่ทันที** |

**ไม่ต้องส่งโค้ด Swift อีก · ไม่ต้องส่งลิงก์รีโปส่วนตัว · ไม่ต้องให้ C เข้า workspace ของ GPT**
งานที่ทำไปแล้วไม่เสียเปล่า — สิ่งที่ต้องการคือ**เนื้อในของแบบ**ที่ GPT ออกไว้แล้ว แค่เขียนออกมาเป็นสเปก

## 2. ทำไมถึงเปลี่ยน (ไม่ใช่เรื่องคุณภาพงาน)

1. **ทางส่งของถึงทีมช้ากว่าตัวงานมาก** — แอป native ต้องมีบัญชี Apple Developer + TestFlight + ลงทีละเครื่อง
   ต่อให้โค้ดเสร็จวันนี้ ทีม 7 คนก็ยังใช้ไม่ได้อีกหลายสัปดาห์
2. **ทางส่งที่เร็วกว่ามีอยู่แล้วและเปิดใช้ได้วันนี้** — C ยิงตรวจสดวันนี้:
   `https://app.dnaev.com/manifest.webmanifest` = **200** · `"display": "standalone"` · `sw.js` = **200**
   แปลว่าแอปเว็บ **เป็น PWA อยู่แล้ว**: ทีมเปิดบนมือถือ → กด "เพิ่มไปยังหน้าจอโฮม" → ได้ไอคอนเป็นแอปเต็มจอ
   ไม่ผ่าน App Store ไม่ต้องเซ็นใบอนุญาต และมีของจริงครบแล้ว: ล็อกอิน · สิทธิ์รายคน · กำแพง PDPA · ข้อมูลสด · สูตรเงิน
3. **GPT ต่อข้อมูลจริงไม่ได้ตามกติกา** (ถูกต้องแล้ว ไม่แก้) — งานฝั่งนั้นเลยติดอยู่ที่ fixture ตลอด
   ส่วน C ต่อข้อมูลจริงได้ทันทีเพราะถือรีโปแอปกับ production อยู่แล้ว

**แอป native ยังไม่ถูกยกเลิก** — แค่ไม่ใช่ "ทางส่งของ" ของรอบนี้

## 3. รูปแบบที่ต้องส่งมา (สำคัญที่สุด — ผิดรูปแบบ = ต้องวิ่งถาม-ตอบอีกรอบ)

**หนึ่งการ์ด = หนึ่งบล็อกแบบนี้** เขียนใน `.md` ธรรมดา ไม่ต้องมีโค้ด:

```
### การ์ด: ปิดจ๊อบรับคืนรถ
เกิดเมื่อ:      ถึงเวลานัดคืนรถ หรือเจ้าของแตะ [เสร็จแล้ว] ในการ์ดก่อนหน้า
ลำดับในกล่อง:   บนสุด (งานวันนี้มาก่อนเสมอ)
บรรทัดหัว:      "รับคืน · {รหัสรถ} · {ชื่อเล่นลูกค้า}"        ← ตัวหนา 17px
บรรทัดรอง:      "วันนี้ 16:00 · เช่า 3 วัน"                  ← สีจาง 13px
เนื้อกลาง:      แถวรายการหัก: "ค่าชาร์จ ฿150" (แก้ได้)
ปุ่ม:           [ปิดจ๊อบ ✓] = ปุ่มหลัก เต็มความกว้าง 48px สูง
                [แก้ไข] = ปุ่มรอง ตัวหนังสือล้วน ไม่มีพื้น
ป้ายเตือน:      🟡 "มัดจำยังไม่ครบ ฿1,000" — ติดมุมขวาบน ไม่บล็อกปุ่ม
สถานะ 1 ยังไม่แตะ:  พื้นขาว ขอบซ้ายหนา 4px สีส้ม
สถานะ 2 แตะแล้ว:    พื้นเทาจาง ปุ่มหาย เหลือข้อความ "ปิดจ๊อบแล้ว 16:02"
สถานะ 3 ติดป้าย:    ขอบซ้ายเป็นสีเหลือง + ป้ายเตือนโผล่
ช่องที่ต้องมี:  รหัสรถ, ชื่อเล่นลูกค้า, เวลานัด, จำนวนวัน, รายการหัก[], ยอดคืน
```

พร้อม **1 ภาพต่อ 1 หน้าจอ** (PNG กว้าง 390px = ขนาด iPhone จริง) วางคู่กันในไฟล์เดียวกัน
ภาพเป็น mockup ก็ได้ ไม่ต้องเป็นภาพจากแอปที่รันได้

**สิ่งที่ทำให้ประกอบได้ทันที** — ระบุ 6 อย่างนี้ทุกการ์ด: ลำดับ · ข้อความ (พร้อมชื่อตัวแปรในปีกกา) · ปุ่มไหนหลัก/รอง · ป้ายเตือนวางตรงไหน · สถานะ 3 แบบหน้าตาอย่างไร · ต้องใช้ข้อมูลช่องไหนบ้าง

## 3.5 ⚡ ทางลัด — ถ้าจอ 1-2-3 สร้างไว้แล้ว ไม่ต้องออกแบบใหม่

รายงาน `2026-09-08-native-09-received.md` เขียนไว้เองว่าทำแล้ว:
*"default app เป็น SwiftUI กล่องเดียว พร้อมตัวอย่างการ์ด 12 ชนิด, เธรดใบจอง และรถ/เดือน"*
— **นั่นคือจอ 1-2-3 ครบแล้ว** เจ้าของจึงสั่งว่า **"เอางานล่าสุดที่ทำไว้ส่งมาเลย"**

**อย่ารื้อทำใหม่ · อย่าออกแบบซ้ำ** — เอาของที่มีอยู่ในเครื่องแปลงเป็นสเปกก็พอ:

1. **แคปหน้าจอจากแอปที่รันอยู่แล้ว** — Simulator iPhone ก็ได้ ส่งเป็น `.png` กว้างเท่าไรก็ได้
   ขอ 3 ภาพเป็นอย่างน้อย: กล่องเดียวเลื่อนยาว · เธรดใบจอง 1 ใบ · การ์ดปิดจ๊อบตอนกางออก
   ยิ่งแคปการ์ดครบ 12 ชนิดยิ่งดี (จะกี่ภาพก็ได้)
2. **เขียนบล็อกตามข้อ 3 ให้แต่ละการ์ดที่ทำไปแล้ว** — อ่านจากโค้ดตัวเองแล้วถอดออกมาเป็นข้อความ
   ไม่ต้องแม่นระดับพิกเซล บอกลำดับ/ข้อความ/ปุ่ม/ป้าย/สถานะ/ช่องข้อมูล ก็พอ
3. **ค่าสีกับระยะที่ใช้จริงในแอป Swift** เทียบกับตารางโทเคนข้อ 5 ว่าตัวไหนตรงตัวไหนต่าง
   ต่างตรงไหนบอกมา C จะเลือกให้ว่าจะยึดของฝั่งไหน

**ส่งภาพอย่างเดียวก่อนก็เริ่มได้** — C ดูภาพแล้วประกอบไปพลาง ๆ ได้ทันที
สเปกข้อความตามมาทีหลังในไฟล์เดียวกันหรือคนละไฟล์ก็ได้ ไม่ต้องรอให้ครบ

⛔ **ยังห้ามส่งโค้ด Swift มาที่รีโปนี้** (รีโปสาธารณะ + ประกอบไม่ได้อยู่ดี) — ส่งภาพกับข้อความเท่านั้น

## 7. 🔴 การ์ดที่ต้องออกแบบก่อนเพื่อน — มีหลักฐานว่าเสียเงินอยู่จริง

C ยิงดูตัวเลขสดจาก production วันนี้ (8 ก.ย. 69) พบว่า **หน้าการเงินอ่านไม่ออกแล้ว**:

|---|---|---|
| พ.ค. 69 | 19 ใบ | 181,510 |
| มิ.ย. 69 | 18 ใบ | 156,635 |
| ก.ค. 69 | 21 ใบ | 147,593 |
| **ส.ค. 69** | **5 ใบ** | **16,450** |
| **ก.ย. 69** | **0 ใบ** | **0** |

ไม่ใช่โค้ดพัง — สูตรการเงินนับเฉพาะใบสถานะ `confirmed/active/completed/returned`
แต่ **ทีมหยุดเลื่อนสถานะตั้งแต่ ส.ค.** ใบเลยค้างที่ `pending` ทั้งที่รถออกไปจริงและเก็บเงินมาแล้ว:
**ส.ค. ตกหล่น 14 ใบ (มูลค่า 152,600 บาท · รับเงินมาแล้ว 61,600) · ก.ย. ตกหล่น 3 ใบ (44,300 บาท · รับแล้ว 39,300)**

ตรงกับหลักฐานที่เคยส่งไปแล้วในข้อเสนอเป๊ะ ๆ: `released_at` = **0/109 ใบ** (ปุ่มปล่อยรถไม่เคยถูกใช้เลย)
→ **สาเหตุคือไม่มีปุ่มปิดจ๊อบที่ใช้ได้จริง** ซึ่งคือการ์ด "ปิดจ๊อบรับคืนรถ" พอดี

**ดังนั้นในไฟล์ที่ 1 ขอให้ออกแบบ 3 ใบนี้ก่อน** แล้วส่งมาได้เลยไม่ต้องรอครบ 12:
1. **ปิดจ๊อบรับคืนรถ** — ตัวปลดล็อกเรื่องเงินทั้งก้อน
2. **คืนเงินประกัน** — ตอนนี้ค้างเลยกำหนด **18 ใบ** (เงินของลูกค้าที่ยังไม่ได้คืน)
3. **สรุปวันนี้** — ตัวที่ทำให้เจ้าของเห็นภาพรวมโดยไม่ต้องเปิดหน้ากำไร
