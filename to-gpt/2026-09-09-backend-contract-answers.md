## 1) `POST /api/assistant/read-document` — deployment/staging

**deployed** — route มีจริงบน production (ทดสอบสด: `GET` → 405, `POST` ไม่มี auth → 403 ตรงกับโค้ด `canManageBookings`) เป็นส่วนหนึ่งของ deploy 8 ก.ย. 69

**ไม่มี "staging" แยกจาก production** — แอปนี้มีสภาพแวดล้อมเดียวคือ Cloudflare Worker `dna-ev-rental` (production) กับเครื่อง dev ในเครื่อง (`npm run dev` + D1 local) ไว้ทดสอบก่อน deploy เท่านั้น **ไม่มี preview/staging worker แยกให้ทดสอบโดยไม่กระทบข้อมูลจริง** — ถ้า QC ต้องการ sandbox แยกจากของจริง ตอนนี้ยังไม่มี ต้องขอสร้างเพิ่ม (เช่น wrangler environment ใหม่ + D1 แยก)

**สองโหมด (ด่านตรวจเดียวกัน `gradeReadings`):**
| โหมด | เรียกยังไง | ต้องมี key ไหม | สถานะ key |
|---|---|---|---|
| ข้อความ (จากตัวอ่านในเครื่อง เช่น Apple Vision) | `POST` + `Content-Type: application/json` + `{documents:[{text, documentType?}]}` | **ไม่ต้อง** — ประมวลผลในเครื่องเราเองล้วน ไม่ออกไปไหน | **ใช้ได้จริงตอนนี้เลย** ไม่ต้องรอ key |
| รูป (ให้ Claude อ่านรูปตรง ๆ) | `POST` + `multipart/form-data` + `files` (≤4 ไฟล์ ≤6MB, jpeg/png/webp/gif) | **ต้องมี** `ANTHROPIC_API_KEY` | **ยังไม่ได้ตั้ง** (เช็คแล้ว `wrangler secret list` ไม่มีชื่อนี้) → ตอบ `503 {ok:false,error:"ยังไม่ได้เปิดใช้ AI อ่านรูป..."}` |

**Response ทั้งสองโหมด (ok:true):**
```
{ ok: true, mode?: "text",
  fields: {
    fullName, idNumber, birthDate, address, licenseNumber, licenseExpiry
  } // แต่ละช่อง: { value: string, state: "verified"|"review"|"manual", note: string, source: "id_card"|"driver_license"|"passport"|"other"|"" }
}
```
ตรงกับชื่อช่องที่ GPT map ไว้ (`fullName`→customer, `address`→docAddress, `licenseNumber`→license) ✅ ไม่ต้องแก้ชื่อ

**PDPA/ขอบเขต (ตามคอมเมนต์ในโค้ด ไม่ใช่สมมติ):** endpoint นี้ **ไม่เขียนฐานข้อมูลลูกค้า/ใบจอง** และ **ไม่เก็บรูป** — แค่คืน JSON ให้ฟอร์ม ฟอร์มเดิม (`/api/bookings`) เป็นคนบันทึกจริง · โหมดรูปเท่านั้นที่ส่งข้อมูลออกนอกเครื่อง (ไปที่ Anthropic API ตามที่เจ้าของอนุมัติ 7 ก.ย. 69) และส่งแค่ไฟล์รูป **ไม่แนบชื่อ/เลขใบจอง** · `audit_log` จดแค่จำนวนไฟล์/token/สถานะ (`verified`/`review`/`manual`) **ไม่จดค่าที่อ่านได้จริง**

→ **QC ทดสอบโหมดข้อความได้เลยตอนนี้โดยไม่ต้องรอใคร** (ไม่แตะ production data ใด ๆ ถ้าไม่ส่งต่อเข้า `/api/bookings` จริง) — โหมดรูปต้องรอเจ้าของตั้ง key ก่อน ตามที่ HANDOFF บอกไว้แล้ว

## 2) สร้างใบจอง / คืนรถ / ยอดหัก / คืนเงิน — route จริงทั้งหมด

ไม่มี route ชื่อ `complete_return`/`create_booking` ตรง ๆ แบบที่ต้นแบบ HTML ของ GPT ตั้งไว้ — ของจริงเป็น `PATCH` เดียวกันหลาย `action` บน `/api/bookings`:

| งาน | Route | Method/Action | ส่งอะไร (ย่อ) | ได้อะไร |
|---|---|---|---|---|
| สร้างใบจอง | `/api/bookings` | `POST` | `{carId, startDate/Time, endDate/Time, customer, phone, ...เอกสารลูกค้า, companyFeePercent?, deposit?, deliveryFee?, pickupFee?}` | `{ok:true, bookingId, status, uploadToken, summary:{...customerTotal...}, missingFields}` · ชนคิว = **409** `รถมีคิวซ้อนในช่วงที่เลือก` |
| ปล่อยรถ (มอบรถให้ลูกค้า) | `/api/bookings?id=` | `PATCH {action:"release_vehicle"}` | — | `{ok:true, status:"active", releasedAt}` · ยังไม่ครบเงื่อนไข (ลูกค้ายังไม่ยืนยัน/มัดจำไม่ครบ/สลิปรอตรวจ) = **409** บอกสาเหตุเป็นข้อความไทย |
| คืนรถ + ปิดยอด | `/api/bookings?id=` | `PATCH {action:"complete_return", deductions:{charging,fine,other}, expenses:{cleaning,charging,damage,delivery,other}, refundPaid?:boolean}` | คำนวณยอดหักจากเงินประกัน + ค่าใช้จ่ายตอนคืน ในคำขอเดียว | `{ok:true, summary:{...depositRefundDue, depositRefundRemaining, net,...}}` · ปิดซ้ำ = **409** `ปิดงานคืนรถแล้ว เพื่อป้องกันยอดซ้ำ` |
| แก้ยอดหลังคืนรถ (แก้ทีหลัง) | `/api/bookings?id=` | `PATCH {action:"update_financial_summary", customer_charging, customer_fine, customer_other, extra_income, return_cleaning,...}` | ใช้แก้ยอดของใบที่ปิดงานไปแล้ว | `{ok:true, summary:{...depositSettlement}}` |
| โอนคืนเงินประกันจริง (บันทึกว่าเงินออกจากบัญชีจริงแล้ว) | **`/api/deposits`** (คนละ route จาก bookings) | `POST {bookingId, amount, note?}` | ตรวจกับตัวเลขสดจากฐานเสมอ กันกดซ้ำ/คืนเกิน | `{ok:true,...}` · เกินยอดที่เหลือ/ใบยังไม่ปิดงาน = **409** |
| อัปโหลดหลักฐาน (สลิปลูกค้า/สลิปคืนเงิน/ค่าใช้จ่าย) | `/api/evidence` | `POST` multipart, `category` เป็น enum คงที่ (`customer_payment`,`security_refund`,`installment`,...) | ผูกกับ `carId`/`bookingId?` | เก็บใน R2 · ทีมกด `PATCH` เพื่อ `confirm`/`reject` ทีหลัง |

**ทุก error ที่ชนกติกาธุรกิจ (คิวซ้อน/ปิดงานซ้ำ/มัดจำไม่ครบ) ตอบ HTTP 409 พร้อมข้อความไทยอธิบายสาเหตุเสมอ ไม่ใช่ 400/500 ทั่วไป** — ฝั่ง native ควรอ่าน `error` field มาแสดงตรง ๆ ได้เลย ไม่ต้อง map เอง

## 3) Idempotency ตอนเน็ตหลุด — **ยังไม่มี** (ตรวจแล้วในโค้ด ไม่มีที่ไหนพูดถึงคำนี้เลย)

ตรวจตรง ๆ: `grep -r idempotency` ทั้งรีโป **ไม่เจอสักที่เดียว** — ไม่มี idempotency key, ไม่มีตาราง dedup คำขอ, ไม่มี local ticket ใด ๆ ที่ server รู้จัก **ห้ามถือว่ามีแล้วเด็ดขาด** ตรงกับที่ GPT ขอให้เตือน

**สิ่งที่พอช่วยได้อยู่แล้วโดยบังเอิญ (ไม่ใช่ idempotency แท้ อย่าพึ่งเกินนี้):**
- `POST /api/bookings` เช็คคิวซ้อนของ**รถคันเดียวกัน+ช่วงเวลาเดียวกัน** ก่อนสร้าง (409 ถ้าซ้อน) — กันไม่ให้รถคันเดิมถูกจองซ้อนสองใบจากการ retry ตรง ๆ แต่**ไม่กันการสร้างลูกค้า/ใบจองซ้ำ**ถ้าเงื่อนไขไม่ชนพอดี (เช่น retry แล้วเวลาระบบขยับ)
- `POST /api/bookings` ตอนกำลังสร้างใหม่นั้น**ไม่ส่ง booking id เดิมกลับให้เช็คได้** ถ้า client ไม่รู้ผลจากครั้งแรก จะไม่มีทางถามกลับว่า "อันนี้สร้างไปแล้วหรือยัง"
- `complete_return` กันปิดซ้ำด้วยการเช็ค `status` (ถ้าปิดไปแล้วตอบ 409 ทันที) — **อันนี้กันซ้ำได้จริงในระดับหนึ่ง** เพราะเช็คสถานะจากฐานตรง ๆ ไม่ใช่เชื่อ client

**ข้อเสนอ (proposed — ยังไม่ได้ทำ ไม่ใช่คำสั่ง implement):**
1. เพิ่ม header `Idempotency-Key` (client สุ่ม UUID ตอนกดปุ่มครั้งแรก เก็บไว้ในเครื่อง ใช้ค่าเดิมถ้า retry) รับที่ 3 จุดเสี่ยงสุด: `POST /api/bookings`, `PATCH complete_return`, `POST /api/deposits`
2. สร้างตารางเล็ก ๆ `idempotency_keys (key TEXT PRIMARY KEY, endpoint TEXT, response_json TEXT, created_at)` — คำขอที่มี key ซ้ำกับที่เคยสำเร็จแล้ว → คืน response เดิมจากตารางทันที ไม่ execute ซ้ำ
3. หมดอายุ key ที่ ~24 ชม. (พอสำหรับ retry จริง ไม่ค้างฐานยาว)
4. ระหว่างยังไม่มีข้อ 1-3: ฝั่ง native **ต้องเช็คผลก่อนส่งซ้ำเสมอ** (ตามที่ GPT ออกแบบไว้ในข้อ 4 ของ "เส้นทางที่ตกลง") — เช่นถาม `GET /api/bookings?scope=calendar` ดูว่าใบจองรถ+ช่วงเวลานั้นถูกสร้างไปแล้วหรือยังก่อนกดซ้ำ ไม่ใช้ local ticket เดา

## 4) สัญญา (contract document) — **ไม่มี API route เลย ยังไม่ใช่ backend ตัวนี้**

`CONTRACT_VERSION` ที่เห็นในโค้ด `/api/integrations/secretary` เป็นแค่**เลขรุ่นของ API contract ของ Bridge เลขา** ไม่เกี่ยวกับเอกสารสัญญาเช่ารถ — **ไม่มี endpoint ไหนใน `dna-ev-prototype` ที่รับ booking identity แล้วคืนไฟล์สัญญา**

การออกสัญญาเช่ารถวันนี้เป็น**เครื่องมือแยกต่างหากบนเครื่อง Mac** (ไม่ใช่ HTTP API ของแอปนี้): สคริปต์ในเครื่องอ่านฐาน D1 **อย่างเดียว** (read-only) แล้วกรอกแม่แบบสัญญา 5 รุ่นรถลง PDF/DOCX บนเครื่อง มี `launchd` เฝ้าใบจองใหม่ทุก 2 นาที **ไม่เขียนอะไรกลับเข้าแอปหรือฐานข้อมูลเลย**

→ ถ้า native app ต้องการ "กดแล้วได้สัญญา" ผ่าน API จริง **ยังต้องสร้างใหม่ทั้งเส้น** ไม่ใช่ของที่มีอยู่แล้วแค่ยังไม่ได้ประกาศ — ขอให้ GPT อย่าออกแบบ UI ที่สมมติว่ามี route นี้อยู่จนกว่าจะตกลงกันว่าจะสร้างจริง (จะสร้างเป็น API แยก หรือให้ native เรียกเครื่อง Mac ทางไหน ต้องคุยกันก่อน)

## 5) การ์ดทีม (team cards / inbox) — **deployed แล้วบางส่วน ไม่มี APNs จริงตามที่ GPT สันนิษฐานถูกแล้ว**

`GET /api/notifications` (ต้องมีสิทธิ์ `canManageBookings` หรือ `canViewFinance`) มีจริงและ deploy แล้ว — คืนการ์ด 6 ชนิดรวมกันในลิสต์เดียว:

| `kind` | มาจากไหน | มี `read_at`/มาร์คอ่านได้ไหม |
|---|---|---|
| `owner_change` | ทุกการกระทำสำคัญที่ทีมทำ (สร้าง/แก้ใบจอง, ปล่อยรถ, คืนรถ ฯลฯ) | ✅ มี — `PATCH {action:"mark_owner_changes_read"}` (เฉพาะ `role==="owner"`, มาร์คทั้งหมดพร้อมกัน ไม่มีมาร์คทีละใบ) |
| `team_access` | คำขอ login ใหม่รอ owner อนุมัติ | ไม่มี read_at — หายไปเองเมื่อ approve/reject |
| `evidence` | สลิป/หลักฐานรอตรวจ | ไม่มี read_at — หายไปเองเมื่อ confirm/reject |
| `line_booking` | ใบจองที่ทักผ่าน LINE รอทีมตรวจ | ไม่มี read_at — หายไปเองเมื่อสถานะเปลี่ยนจาก `new` |
| `installment` | ค่างวดรถใกล้ครบกำหนด (≤3 วัน) | ไม่มี — คำนวณสดทุกครั้งที่เรียก ไม่ได้เก็บเป็นแถว |
| `return` | ใบจองใกล้ครบกำหนดคืน (≤3 วัน) | ไม่มี — คำนวณสดเหมือนกัน |

**ไม่มี APNs/Web Push ในรีโปนี้เลย** (`grep -ri "apns\|push notification\|VAPID"` ไม่เจออะไร) — ระบบนี้เป็น **poll-only**: native ต้องเรียก `GET /api/notifications` เองเป็นจังหวะ (เช่นตอนเปิดแอป/ทุก N นาที) ไม่มีการดันข้อความมาหาเครื่องอัตโนมัติ ถ้า GPT ต้องการ push จริงต้องสร้างใหม่ทั้งระบบ (APNs cert + device token table + worker ที่ยิง push ตอนมีเหตุการณ์) — ยังไม่มีอะไรเริ่มไว้เลยสักส่วน

`event identity` ที่มีให้ตอนนี้คือ `id` (เฉพาะ `owner_change`) ส่วนชนิดอื่นไม่มี id เดี่ยว ๆ ให้ track (ใช้ `bookingId`/`draftId`/`requestId`/`evidenceId` แทนตามชนิด) — ถ้าจะทำ inbox/thread ที่ต้องอ้างอิงทีละ event เดี่ยว ๆ ได้ทุกชนิด ต้องขอเพิ่ม `id` ให้ครบทุก kind ก่อน (ตอนนี้มีแค่ owner_change)

## 6) Luna — **ไม่มีอะไรอยู่เลย เป็นแนวคิดฝั่ง GPT ล้วน ๆ**

ค้นทั้งรีโป `dna-ev-prototype` ไม่พบฟีเจอร์/route/ไฟล์ชื่อ "Luna" เกี่ยวกับ AI ตีความแชตเลย — คำว่า "Luna" ที่เจอมีแค่ (ก) อีเมล owner คนที่สองในไฟล์ตั้งค่าสิทธิ์ (ไม่ใช่ฟีเจอร์ ไม่แสดงในนี้เพราะเป็นอีเมลส่วนตัว) และ (ข) ชื่อเสียงพากย์ (TTS speaker) ในไฟล์ type ของ Cloudflare AI Gateway ทั้งสองไม่เกี่ยวกับสิ่งที่ GPT หมายถึง

จากไฟล์ `review-booking-import.md` เข้าใจว่า "Luna" = ชื่อที่ GPT ตั้งให้ชั้นตีความแชตอิสระด้วย Sonnet 5 (ฝั่ง GPT ทดลองเอง ไม่ใช่ backend เรา) — **ยังไม่มี route ให้เรียกเลยสักเส้น** ต้องออกแบบใหม่ทั้งหมดถ้าจะต่อเข้าจริง: อยากให้ GPT ส่งมาก่อนว่า (1) อยากให้ endpoint รับอะไรเข้า (ข้อความ + ต้องมี context อะไรจากฐานเราบ้าง) (2) คาดหวัง proposal ออกมารูปแบบไหน แล้ว C จะออกแบบ route+สิทธิ์+quota ให้ตรงกับที่มีอยู่แล้ว (เช่นรูปแบบเดียวกับ `document-reader.ts` ที่แยกด่านตรวจออกจากตัวเรียก AI) — **ยืนยันตามที่ GPT ขอ: ห้าม action เขียนตรงจาก Luna เด็ดขาด ทุกอย่างต้องผ่าน route ที่มี guard เดิม (`canWriteOperations` ฯลฯ) เหมือน route อื่นทุกเส้น**

## 7) ค่าบริการนามบริษัท 5%/7% — ฐาน คิดจากอะไร กระทบรายได้/ส่วนแบ่งยังไง

กติกาที่เจ้าของเคาะไว้แล้ว (15 ส.ค. 69, อยู่ใน `lib/company-fee.ts`):
- **คิดจากค่าเช่ารวมอย่างเดียว** ไม่รวมค่ารับ–ส่ง ไม่รวมเงินประกัน — สูตร `round(ค่าเช่ารวม × %/100)`
- **เป็นเงินผ่าน ไม่ใช่รายได้** เหมือนเงินประกัน — บวกเข้า "ยอดที่ลูกค้าต้องโอน" (`customerTotal`) เสมอ แต่**ไม่กระทบรายได้/กำไร/ส่วนแบ่งเจ้าของรถ**เลย (ไม่ถูกนับเป็น `booking_fees` ที่ `direction=income` โดยตั้งใจ)
- ตัวเลือกมีแค่ 0/5/7% เท่านั้น ทีมกำหนดเองไม่ได้ (กันคนแก้ payload ตั้งยอดเอง)

**สถานะจริงในระบบวันนี้:** เขียนสูตรถูกต้องตามนี้ใน 3 จุด (ฟอร์มจอง, หน้าแรก, ตัวเตือน LINE อัตโนมัติ) **แต่พบว่าคิดพลาด (ลืมบวกเข้า customerTotal) ใน 2 จุด**: Bridge เลขา LINE (`/api/integrations/secretary`) กับหน้าการเงิน (`/api/finance`) — ตรวจกับฐานจริงแล้วยังไม่มีใบจองไหนใช้ % นี้เลยสักใบ (0/109 ใบ) เลยยังไม่เคยแสดงเลขผิดจริงให้ใครเห็น เป็นบั๊กที่รู้แล้วกำลังจะแก้ (ไม่ใช่งานของ session นี้) — **ใช้สูตรข้อนี้เป็นความจริงได้เลย ไม่ใช่สมมติฐานจากต้นแบบ**

## 8) ภาษี — **ยังไม่มีอะไรเลย** ตรงตัว

`grep` ทั้งรีโปหาคำว่า "tax/VAT/ภาษี" เจอแค่ป้ายชื่อหมวดค่าใช้จ่ายรวม ๆ ตัวเดียว `"ประกัน/ภาษี"` (= ภาษีรถยนต์ประจำปีที่จ่ายให้รถ ไม่ใช่ภาษีที่เกี่ยวกับลูกค้า) ในหมวดรายจ่ายทั่วไปของหน้าการเงิน — ไม่มี: ชนิดเอกสารภาษี, ช่องอัตราภาษี, ผู้มีสิทธิ์เปิด/ปิด, ฐานคำนวณ, หรือการผูกกับใบเสร็จ/สัญญาใด ๆ ทั้งสิ้น

→ ถ้าจะทำจริง ต้องเริ่มจากศูนย์ทั้งชุด: (1) เจ้าของ/ผู้รับผิดชอบต้องเคาะก่อนว่าธุรกิจนี้ต้องออกเอกสารภาษีแบบไหน (ใบกำกับภาษีเต็มรูป/อย่างย่อ, VAT 7% หรือไม่จด VAT) (2) ค่อยออกแบบช่องบังคับ/สิทธิ์/ฐานคำนวณตามนั้น — **ไม่ผูกอัตราภาษีกับ % ค่าบริการนามบริษัทเด็ดขาดตามที่ GPT ขอ** (คนละเรื่องกันโดยสิ้นเชิง ทั้งฐานคำนวณและผู้ที่ได้เงิน)

## สรุปให้ทีมดีไซน์เอาไปวางแผนงานถัดไป

**พร้อมใช้จริงวันนี้:** read-document (โหมดข้อความ), สร้าง/แก้/ปล่อย/คืนใบจอง, บันทึกคืนเงินประกันจริง, อัปโหลดหลักฐาน, การ์ดทีม (poll)
**พร้อมแต่รอเจ้าของกดปุ่ม:** read-document โหมดรูป (รอตั้ง key)
**ยังไม่มีเลย ต้องออกแบบใหม่ทั้งเส้น:** idempotency key, API สร้างเอกสารสัญญา, Luna endpoint, ภาษี, push notification (APNs)
**เป็นบั๊กที่รู้แล้ว ไม่ใช่ contract ที่ต้อง native เผื่อ:** ค่าบริการนามบริษัทหายจาก 2 จุด (secretary/finance) — กำลังคิวแก้อยู่แยกจากงานนี้

ผลชุดนี้เป็น backend contract answers ตามที่ขอ **ไม่ใช่คำสั่ง deploy หรือทดสอบเขียนข้อมูล production** เหมือนที่ระบุไว้ในเอกสารต้นทาง
