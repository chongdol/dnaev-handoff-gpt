## 3) สูตรการหัก–คืน (`lib/security-deposit.ts`)

```
deductions      = chargingCharge + customerFine + otherDeduction
refundDue       = max(0, deposit − deductions)        ← ยอดที่ต้องคืน
extraCustomerDue = max(0, deductions − deposit)       ← หักเกินประกัน ลูกค้าต้องจ่ายเพิ่ม
returned        = min(ยอดที่โอนจริง, refundDue)        ← clamp ไม่ให้เกิน
refundRemaining = max(0, refundDue − returned)
closed          = (refundDue === 0) || (returned >= refundDue)
```

**ยอดหัก 3 ก้อน** (ตรงกับ `depositDeductionCategories` ในก้อน 3):
`customer_charging` (ค่าชาร์จ) · `customer_fine` (ค่าปรับ) · `customer_other` (อื่น ๆ / ค่าเสียหาย)
ทั้งสามเป็น **รายได้จริงของ DNA EV** แต่ **ไม่ใช่เงินที่ลูกค้าโอนเข้ามาใหม่** → ไม่นับใน `paid`

### 🔴 `returned` กับ `transferred` เป็นคนละตัว — อย่าใช้สลับกัน (`lib/deposit-refund.ts`)

`deposit_returned` ในฐานคือ **ยอดที่โอนออกไปจริง** ซึ่ง**มากกว่ายอดที่ต้องคืนได้**
(ข้อมูลจริง 5 ส.ค. 69 มีใบที่โอนเกินไป **750 บาท**)

| ตัวแปร | ความหมาย | ใช้ทำอะไร |
|---|---|---|
| `returned` | ยอดที่นับเป็นการคืนได้ (clamp แล้ว) | คิดยอดค้างคืน |
| `transferred` | ยอดที่โอนออกไปจริงตามฐาน | หา `overRefunded` เพื่อ**ตามเก็บคืนจากลูกค้า** |
| `overRefunded` | `max(0, transferred − refundDue)` | ยอดที่โอนเกิน — **ไม่ใช่ยอดค้างคืน** |
| `overdueDays` | เลยกำหนดคืนมากี่วัน | นับเฉพาะใบที่ยัง `refundRemaining > 0` |

⚠️ เอา `returned` ไปบวกยอดใหม่เมื่อไร ใบที่โอนเกินจะถูกลบส่วนเกินทิ้งเงียบ ๆ

### ด่านก่อนบันทึกการโอน (`planDepositRefund`)
1. ยอดต้อง > 0 → ไม่งั้น `"กรุณาระบุยอดที่โอนคืนให้มากกว่า 0 บาท"`
2. คืนครบแล้ว → ปฏิเสธ · ถ้าเคยโอนเกิน ข้อความจะบอกตรง ๆ ว่า
   `"ใบนี้โอนคืนเกินไปแล้ว ฿X ต้องตามเก็บคืน ไม่ใช่โอนเพิ่ม"`
3. ยอดเกินที่ค้าง → `"ใบนี้ค้างคืนอยู่ ฿X โอนคืนเกินยอดนี้ไม่ได้"` (เผื่อเศษทศนิยม 0.005)
4. **ตัวเลขที่ใช้ตรวจต้องอ่านสดจากฐานเสมอ ห้ามเชื่อยอดที่หน้าจอส่งมา**
   (กันเคสจริง: กดปุ่มซ้ำแล้วเงินถูกบันทึกสองรอบ)

→ นี่คือคำตอบส่วนหนึ่งของคำถาม idempotency ที่ G ถามมา: **ฝั่งคืนเงินมีด่านกันซ้ำเชิงตรรกะแล้ว**
(ตรวจยอดค้างสดก่อนเขียน) แต่ **ไม่ใช่ idempotency key จริง** — ยิงสองครั้งพร้อมกันยังแข่งกันได้

**อ่านอย่างไร** — `pending` / `confirmed` / `active` ยังไม่ถึงเวลาคืน (รถยังไม่ออกหรือยังวิ่งอยู่) เป็นเรื่องปกติ
ที่ต้องดูคือสามแถวล่าง: **`returned` + `completed` + `cancelled` = 18 ใบ · ส่วนต่าง 86,690 บาท**

⚠️ **นี่คือตัวเลขจากฐาน ไม่ใช่ข้อสรุปว่าค้างลูกค้าจริง 86,690** — ส่วนต่างอาจมาจาก
(ก) หักค่าเสียหาย/ค่าปรับจริงแต่ไม่ได้บันทึกเป็นยอดหัก (ยอดหักทั้งระบบมีแค่ **1 แถว 500 บาท**)
(ข) คืนสดแล้วไม่ได้บันทึก (ค) ใบเก่าที่ import มาไม่ครบ
→ **ต้องให้คนตรวจทีละใบ** ระบบตอบแทนไม่ได้ · ผมยังไม่แตะข้อมูลใด ๆ

→ สำหรับดีไซน์: จอ "คืนเงินประกัน" ต้องแยกให้เห็น **"ยังไม่ถึงเวลาคืน"** กับ **"ถึงเวลาแล้วยังไม่คืน"**
ไม่ใช่โชว์ยอดค้างรวมก้อนเดียว (274,685) ซึ่งทำให้ตกใจโดยไม่จำเป็น

## 6) หลักฐานการเงิน (`financial_evidence` 60 แถวจริง)

| category | status | แถว | ยอดรวม |
|---|---|---|---|
| `customer_payment` | pending | 20 | 69,450 |
| `id_card` | pending | 15 | 0 |
| `driver_license` | pending | 13 | 0 |
| `address_proof` | pending | 8 | 0 |
| `customer_with_car` | pending | 3 | 0 |
| `customer_payment` | **confirmed** | 1 | 32,550 |

### สามเรื่องที่ต้องรู้ก่อนออกแบบจอหลักฐาน
1. **59 จาก 60 แถวเป็น `pending`** — ขั้นตอน "อนุมัติหลักฐาน" มีจริงในระบบ (`confirmedBy` · `confirmedAt` · `rejectedBy` · `rejectedAt`) แต่แทบไม่มีใครกด
   → จอที่ถือว่า "หลักฐาน confirmed แล้วค่อยไปต่อ" จะติดตันกับข้อมูลจริงเกือบทั้งหมด
2. **ไม่มี category สำหรับ "หลักฐานการคืนเงิน" เลย** — ที่มีคือหลักฐาน*ลูกค้าจ่ายเข้ามา* กับ*เอกสารยืนยันตัวตน*
   → flow `refund evidence` ที่ต้นแบบทดลองไว้ **ยังไม่มีที่ยืนในฐานปัจจุบัน** ต้องเพิ่ม category ใหม่ + ตกลงกันก่อน
3. เอกสารยืนยันตัวตน (`id_card` · `driver_license` · `address_proof` · `customer_with_car`) มี `amount = 0` เสมอ
   → อย่าเอา `amount` ไปใช้แยกชนิดหลักฐาน ให้ใช้ `category`

ไฟล์เก็บอยู่ R2 (`storageKey` · `originalName` · `contentType` · `sizeBytes`) และมี `driveStatus` (`r2_saved` เป็นค่าเริ่มต้น) + `driveFileUrl` สำหรับสำเนาขึ้น Drive
