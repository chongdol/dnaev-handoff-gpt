## 2. โครงใหม่: 3 หน้าจอ · 3 ท่า · เลขาเริ่มก่อนเสมอ
**3 หน้าจอ** — (1) **กล่องเดียว**: ทุกเหตุการณ์เป็นการ์ดเรียงตามเวลา เลขา AI เป็นคนโพสต์ · (2) **เธรดใบจอง**: กดการ์ดเข้าไปเห็นไทม์ไลน์ใบนั้น จอง→ส่ง→ต่อวัน→รับคืน→คืนประกัน · (3) **ปฏิทินรถ**: ตามสัญญา API v2 ที่ตอบไปแล้ว
**3 ท่าที่เจ้าของทำ (ห้ามมีท่าที่ 4)** — **แตะ** = ยืนยันสิ่งที่ระบบคิดมาให้ · **ตอบประโยคเดียว** = แก้/สั่ง ระบบแปลงเป็นช่องเองแล้วขึ้นการ์ดใหม่ให้แตะ · **ส่งรูป** = บัตร/ใบขับขี่/สลิป/หน้าปัด → ตาอ่าน → การ์ด
**เลขาเริ่มก่อนเสมอ** — เวลาและเหตุการณ์เป็นตัวจุด ไม่ใช่เจ้าของเปิดแอปมาหา: 07:00 การ์ดวันนี้ · ก่อนงาน 1 ชม. · วันครบสัญญา · เงินถึงกำหนด · ลูกค้า LINE ทักมา
**สายพานจากประโยคเดียว** — "คุณตัวอย่างเอา DNA 3 วันที่ 12–15 ส่งบ้าน 2,000/วัน" + รูปบัตร → การ์ดข้อเสนอ (ค้นลูกค้าเก่า · เช็ครถว่าง · คิดราคา/ประกัน) → [ยืนยัน ✓] → ล็อกรถ + สร้างใบ + เกิดงานส่ง/รับ 2 ชิ้นเข้าคิว + สัญญาจากแม่แบบ + นัดหมายเด้งเองตามวันในสัญญา + เด้งบอกทีม — **ทั้งหมดจากแตะเดียว**

### นับขั้นตอน (ประมาณการ — ไม่ใช่ตัวเลขวัดจริง)

นับเฉพาะจังหวะที่พี่ต้อง "ลงมือ" จริง (ไม่นับอ่านผ่าน) เทียบ 6 งานหลักของวันนี้:

| งาน | แบบเดิม (เปิดแอป→เมนู→ฟอร์ม→กรอก→บันทึก) | แบบกล่องเดียว |
|---|---|---|
| ตอบลูกค้าใหม่ LINE | เปิดแอปเช็ครถว่าง → เปิด LINE OA → พิมพ์ตอบเอง ≈ 5–6 ครั้ง | แตะ [ส่ง] = 1 ครั้ง |
| โพสต์ตอบลีด FB | เปิดเฟซบุ๊ก → หาโพสต์ → พิมพ์คอมเมนต์ ≈ 3–4 ครั้ง | แตะ [ส่ง] = 1 ครั้ง |
| ส่งรถ | เปิดแอป → เมนูใบจอง → หาใบ → กดปล่อยรถ → กรอกเวลา/กม./แบต → บันทึก ≈ 6–7 ครั้ง | แตะ + ส่งรูป = 2 ครั้ง |
| รับสลิป | เปิดแอป → หาใบ → เปิดฟอร์มการเงิน → กรอกยอด/วันที่/เลือกก้อน → บันทึก ≈ 5–6 ครั้ง | ส่งรูป + แตะ = 2 ครั้ง |
| ต่อวันทางโทรศัพท์ | วางสาย → เปิดแอป → หาใบ → แก้วันที่ → คำนวณราคาเอง → บันทึก ≈ 5–6 ครั้ง | พิมพ์ 1 ประโยค + แตะยืนยัน = 2 ครั้ง |
| รับคืน + คืนประกัน | เปิดแอป → หาใบ → กรอกกม./แบต/ค่าเสียหาย → คำนวณเอง → หน้าธุรกรรม → กรอกคืนเงิน → บันทึก ≈ 8–10 ครั้ง | แตะรับคืน + ส่งรูป + แตะโอนคืน = 3 ครั้ง |

รวมทั้งวัน: แบบเดิมประมาณ **32–39 ครั้งที่ต้องแตะ/พิมพ์** ต่อแบบกล่องเดียวประมาณ **11 ครั้ง** — คือลดลงราว 3–4 เท่า ตัวเลขนี้เป็นการประมาณจากขั้นตอนทั่วไปของแอปฟอร์มเดิม ไม่ได้จับเวลาจริงเทียบเคียง ต้องวัดซ้ำอีกทีตอนมีของจริงให้ลองใช้

## ฉ. ฝั่งลูกค้าอยู่ใน LINE เท่านั้น

ลูกค้าไม่ต้องลงแอป ไม่ต้องรู้ด้วยซ้ำว่ามีแอป — ลูกค้าทัก LINE เหมือนเดิมทุกอย่าง มีสองทางที่คำถามไปถึง:

**1. เลขาบอทตอบเองทันที (มีอยู่แล้ว ไม่ต้องสร้างใหม่)** — คำถามซ้ำที่มีคำตอบตายตัวหรือดึงจากเครื่องมือได้ตรง ๆ ไม่ต้องผ่านคน: ทักทาย/ขอบคุณ, ที่อยู่ร้าน, ทวนวัน-เวลาที่ลูกค้าบอกมา และ **ถ้าต่อ API เช็คคิวรถจริงของแอปได้เชื่อถือ** — "ว่างไหม/ราคา/ค่าส่งของรุ่น+วันที่ที่ระบุชัด" ก็ตอบเองได้เช่นกัน เพราะคำตอบมาจากเครื่องมือ ไม่ใช่จากความจำหรือเดา (หลักการเดียวกับที่สกิลแอดมินตอบลูกค้าเขียนไว้อยู่แล้ว: "ต้องมาจากเครื่องมือหรือคลังคำตอบเท่านั้น") — **ข้อนี้เปลี่ยนจากกติกาปัจจุบันที่บังคับส่งทีมทุกครั้งเรื่องราคา/คิว เป็นข้อเสนอที่ต้องคุยกับเจ้าของก่อนเปิดใช้จริง เพราะแตะกติกาที่เจ้าของเคาะไว้ 9 ส.ค. 69**

**2. ขึ้นการ์ดในกล่องเดียวให้พี่แตะ** — คำถาม/สถานการณ์ที่ไม่ชัวร์หรือแตะเงิน: ต่อรอง/ขอลดราคา/ขอโปร, เคลม/ร้องเรียน, เช่ารายปี, อะไรก็ตามที่บอทไม่มั่นใจ (ด่าน `statesShopFacts()` เดิม) — การ์ดขึ้นเป็น "คุณตัวอย่างถาม [คำถาม]" พร้อม**ร่างคำตอบสำเร็จรูปตามบทแอดมิน**ให้อ่านผ่านตาเดียว พี่แตะ **[ส่ง]** ก็จบ หรือแตะ **[แก้]** พิมพ์ประโยคใหม่ก่อนส่งก็ได้

**ตอบยังไงไม่กินโควตา push** — การ์ดที่พี่แตะ [ส่ง] ทั้งหมดออกทาง **reply token** (คนละก้อนกับ push, ฟรี ไม่จำกัด) เพราะมี token ค้างอยู่แล้วจากข้อความที่ลูกค้าทักเข้ามา ไม่ใช่ระบบยิงหาลูกค้าเอง

**กติกาโควตา push 300 ใบ/เดือน (แผนฟรี ปัจจุบัน)** — เลขากับตัวเตือนงานใช้ก้อนเดียวกันอยู่แล้ว (ปัจจุบัน ~3.7 ข้อความ/วัน) การ์ดในกล่องเดียวเข้ามาแทนที่**การเตือนทีมทั้งหมด** (ส่ง/รับคืน/ครบสัญญา/เงินถึงกำหนด) — เพราะการ์ดอยู่ในแอป ไม่ใช่ LINE message จึงไม่กินโควตาเลย เท่ากับ**คืนโควตาที่เคยใช้เตือนทีมกลับมาทั้งหมด** เหลือ push ไว้ใช้กับลูกค้าอย่างเดียว (ทวงเงิน/แจ้งสถานะที่ยิงเอง ไม่ใช่ reply) และยังต้องนับรวมเป็นก้อนเดียวต่อรอบเหมือนกติกาเดิม ห้ามยิงแยกรายลูกค้า

## ช. เฟซบุ๊กเข้ากล่องเดียวกัน

**เป็นข้อเสนอ ยังไม่ได้ทำ** — งานยิงลีดเฟซบุ๊ก (ทำบน Mac ผ่านสกิล "ยิงลีด") ตอนนี้แยกขาดจากแอปและ LINE คนละระบบ คนละที่เก็บ แนวทางที่เป็นไปได้: เมื่อทักอินบ็อกซ์ลูกค้าเฟซบุ๊กสำเร็จและลูกค้าตอบกลับสนใจจริง ให้ขึ้นเป็นการ์ด "ลีดเฟซบุ๊ก: [ชื่อ] สนใจ [รุ่น]" ในกล่องเดียวกัน แตะแล้วพี่กรอกต่อเป็นใบจองได้เลยแบบเดียวกับใบจองจาก LINE ไม่ต้องสลับแอป — ต้องมีทางเชื่อมข้อมูลจากเฟซบุ๊ก (Messenger API หรือกึ่งอัตโนมัติแบบที่ยิงลีดทำอยู่) เข้ากล่องเดียว ซึ่งยังไม่มีในสถาปัตยกรรมปัจจุบัน ต้องออกแบบเพิ่ม
## ซ. แม่แบบสัญญารายรุ่น = รูปบัตรเข้า สัญญาออก

สคริปต์ 4 ตัวในสกิล "ทำสัญญา" (`กรอกสัญญา-EX2.py` / `-EX2-นิติบุคคล.py` / `-ORA5.py` / `-DEEPAL.py`) ใช้ฟอร์มต้นฉบับเดียวกัน ต่างกันแค่ค่าคงที่ประจำรุ่น — ช่องที่ต้องกรอกจึงเหมือนกันทุกรุ่น ต่างแค่ตัวเลข:

| กลุ่มช่อง | ตัวอย่างช่อง | ที่มา | ต้องใช้ตา AI ไหม |
|---|---|---|---|
| จากบัตร ปชช. | เลขบัตร 13 หลัก · ชื่อ-สกุล · อายุ · ที่อยู่ | ถ่ายรูปบัตร (ลูกค้าใหม่) หรือคลัง `customers` (ลูกค้าเก่า) | **ใช้** เฉพาะลูกค้าใหม่ — เคยพิสูจน์แล้วในแอป (`lib/document-reader.ts`, Sonnet 5, ✅8ก.ย.69) |
| จากใบขับขี่ | เลขใบขับขี่ · วันออก/วันหมดอายุ | ถ่ายรูปใบขับขี่ (ลูกค้าใหม่) หรือคลัง `license_expiry` | **ใช้** เฉพาะลูกค้าใหม่ — วันหมดอายุอ่านผิด = ปล่อยรถให้คนไม่มีใบขับขี่ ห้ามเดา |
| จากใบจอง | ช่วงเช่า/จำนวนวัน · มัดจำที่โอนแล้ว · ค่าส่ง/ค่ารับคืน · สถานที่ | พี่พิมพ์ตอนสร้างใบจอง หรือดึงจากใบจองที่มีอยู่แล้ว | ไม่ใช้ — ดึงจากฐานตรง ๆ |
| จากตารางรถ | มูลค่ารถในสัญญา · ค่าวิ่งเกิน บ./กม. · ค่าชาร์จไฟ บ./% · เงินประกัน · ทะเบียน (จับคู่คลังรถเท่านั้น ไม่เชื่อจากรูป) | ตารางค่าคงที่ในสคริปต์ + คลัง `cars` | ไม่ใช้ — ค้นฐาน/กติกาตายตัว |
| คงที่ต่อรุ่น | ตัวหนังสือกำกับมูลค่ารถ · ค่าบริการ 5% (เฉพาะ EX2-นิติบุคคล) | เขียนไว้ในสคริปต์แล้ว | ไม่ใช้ |

**ด่านตรวจตายตัวที่มีอยู่แล้ว ทำงานโดยไม่ใช้ AI เลย:**
- เลขบัตร 13 หลัก checksum (`isValidThaiIdNumber`, `lib/thai-documents.ts`)
- 2 สมการยอดเงิน `check_money()`: ส่วนที่เหลือ = ค่าเช่ารวม − มัดจำ, รวมทั้งสิ้น = ส่วนที่เหลือ + ประกัน + ค่าส่ง + ค่ารับคืน + ค่าใช้จ่ายเพิ่ม
- ทะเบียนต้องมีจังหวัดกำกับ + ตรงกับคันในคลัง (`check_plate()`)

**หลักการ "อ่านบัตรครั้งเดียว เก็บเป็นลูกค้า ครั้งหน้า 0 AI":** ช่องจากบัตร/ใบขับขี่ทั้งหมดคือคอลัมน์ในตาราง `customers` อยู่แล้ว (`ค้นลูกค้า.py` ค้นด้วยชื่อ/เบอร์/เลขบัตรได้) — พอเจอในคลัง แม่แบบดึงตรงเข้าช่องทันที ไม่ต้องถ่ายรูปหรือเรียกตา AI อีกเลย

## ฌ. สลิปโอนแล้วจบ

```
อัพสลิป → ตา AI รุ่นเล็กสุด (Haiku 4.5) อ่านยอด/วันที่/เวลา/เลขอ้างอิง
      → กติกาตายตัวจับคู่ก้อนที่ค้าง
          ├─ ยอดตรงก้อนพอดี → โยนเข้าให้เลย + เด้งบอกทีมทันที
          └─ ไม่ตรง → การ์ดให้แตะเลือกก้อน + ป้ายเตือนสีเหลือง (ไม่บล็อก ไม่ใช่ ❌)
      → กันสลิปซ้ำ: เช็คเลขอ้างอิง+เวลาโอนกับสลิปที่เคยรับแล้วในใบจองเดียวกัน ซ้ำ = เตือน ไม่บันทึกซ้ำ
```
อ่านสลิปเป็นงานอ่านตัวเลข/วันที่จากภาพนิ่งสั้น ๆ ไม่ต้องเหตุผลซับซ้อนเหมือนบัตร ใช้โมเดลเล็กสุดพอ — ต่างจากบัตร/ใบขับขี่ที่ผิดแล้วกระทบสิทธิ์ขับรถ

## ญ. แผนต้นทุน AI: ใช้ตาแค่ 3 จุด

| ขั้นในสายพาน | ใช้ AI ไหม | ทำอะไรแทนถ้าไม่ใช้ | รุ่นแนะนำ | เหตุผล |
|---|---|---|---|---|
| รถว่างไหม / ราคาช่วงนี้ | ไม่ใช้ | ค้นฐาน + ขั้นบันไดราคาคงที่ | — | ข้อมูลมีอยู่แล้ว ไม่ต้องตีความ |
| ลูกค้าเก่าไหม | ไม่ใช้ | ค้นฐาน `customers` ด้วยชื่อ/เบอร์ | — | ค้นตรง ๆ แม่นกว่าให้ AI เดา |
| **อ่านบัตร/ใบขับขี่** (ลูกค้าใหม่เท่านั้น) | **ใช้ (ตา)** | — | **Sonnet 5** | ผิดกระทบสิทธิ์ขับรถ/ตัวตน ต้องแม่น มีเทสต์คุมอยู่แล้ว |
| กรอกแม่แบบสัญญา + ตรวจยอด/ทะเบียน | ไม่ใช้ | พิกัดคงที่ในสคริปต์ + `check_money()`/`check_plate()` | — | สูตรตายตัว ไม่มีที่ให้ตีความ |
| สร้างใบจอง / ปล่อยรถ / ปิดจ๊อบ | ไม่ใช้ | เรียก `lib/` เดิมผ่าน API มีอยู่แล้ว | — | ต้องมี audit ห้าม AI เขียนฐานเอง |
| **อ่านสลิปโอนเงิน** | **ใช้ (ตา)** | — | **Haiku 4.5** | อ่านยอด/วันที่สั้น ๆ งานง่ายสุดในสายพาน |
| จับคู่สลิปกับก้อนค้าง | ไม่ใช้ | กติกาตายตัว: ยอดตรงพอดี=auto, ไม่ตรง=การ์ดเลือกเอง | — | เดาไม่ได้เรื่องเงิน ต้องกฎตายตัว |
| ต่อวัน / แก้วันคืน | ไม่ใช้ (ทำบ่อย=ปุ่มสำเร็จรูป) | ปุ่ม "ต่อ 1/3 วัน" ตรง ๆ | — | 2.4 ครั้ง/ใบ = งานประจำ ไม่ต้องตีความประโยค |
| **อ่านหน้าปัด (กม.+% แบต) ตอนคืนรถ** | **ใช้ (ตา)** | — | **Sonnet 5** | ตัวเลขกระทบยอดหักเงินจริง ต้องแม่น |
| คำนวณยอดหักตอนคืน | ไม่ใช้ | สูตร `security-deposit` เดิม (โค้ดล้วน) | — | มีสูตรอยู่แล้ว ไม่ต้องเดา |
| คุยเป็นประโยคอิสระ ("เลื่อนส่งบ่ายสอง") | ใช้ (สมอง คนละงานกับตา) | — | Sonnet 5 (มี tool) | ต้องแปลงประโยคเป็น tool call ให้ถูก เสี่ยงถ้าพลาด — นับแยกจาก 3 จุดตา |

**ประมาณ AI call ต่อใบจอง 1 ใบ**
- ลูกค้าใหม่: อ่านบัตร+ใบขับขี่ 1 ครั้ง (ส่งพร้อมกันในคำขอเดียว) + อ่านสลิป 1 ครั้ง + อ่านหน้าปัดตอนคืน 1 ครั้ง = **3 ครั้ง**
- ลูกค้าเก่า: อ่านสลิป 1 + อ่านหน้าปัด 1 = **2 ครั้ง** (0 ครั้งอ่านบัตร ตามหลัก "ครั้งเดียว")

**ต่อเดือนที่ ~25 ใบ** (สัดส่วนใหม่/เก่าจริงยังไม่มีตัวเลขยืนยัน — สมมติคร่าว ๆ ว่าส่วนใหญ่เป็นลูกค้าเก่า): ราว 55–75 ครั้ง/เดือน รวมทุกจุด บวกคำสั่งประโยคอิสระอีกไม่กี่ครั้งแล้วแต่พี่ใช้บ่อยแค่ไหน

**ประมาณต้นทุนคร่าว ๆ** (คำนวณจากราคาโมเดลจริงในสกิล claude-api: Sonnet 5 = $2/$10 ต่อล้านโทเค็น อินพุต/เอาต์พุต · Haiku 4.5 = $1/$5 — ส่วนจำนวนโทเค็นต่อรูปเป็นค่าประมาณ ต้องวัดจริงด้วย token-count API ตอนใช้งานจริง): 1 ครั้งอ่านบัตร+ใบขับขี่ ~$0.01 · 1 ครั้งอ่านสลิป ~$0.003 · 1 ครั้งอ่านหน้าปัด ~$0.007 → รวมทั้งเดือนต่ำกว่า **$1 (ราวหลักสิบบาท)** — ถูกพอที่จะไม่ต้องกังวลเรื่องต้นทุนถ้าใช้แค่ 3 จุดนี้จริง ๆ

**Prompt caching**: system prompt ของ `document-reader.ts` (คำสั่งด่านตรวจ 3 สถานะ, สคีมา structured output) และชุด tool schema ของ "คุยเป็นประโยค" เป็นข้อความคงที่ ส่งซ้ำทุกคำขอ — ใส่ `cache_control: {type:"ephemeral"}` ที่ท้ายบล็อกนี้ ตัดต้นทุนอินพุตส่วนนี้ลงได้มากในคำขอที่ตามมาภายในไม่กี่นาที คุ้มเฉพาะช่วงพี่ใช้ต่อเนื่อง (ถ่ายรูปหลายใบติดกัน) ไม่คุ้มถ้าห่างกันเป็นชั่วโมง

## ฎ. ขอ GPT ออกแบบ

1. ปุ่ม "📷 อ่านจากรูป" ต้องรับได้ทั้งบัตร+ใบขับขี่พร้อมกันในการ์ดเดียว (ส่งเป็นคำขอ AI ครั้งเดียว ไม่ใช่ 2 ปุ่มแยก)
2. การ์ดผลอ่านต้องโชว์ 3 สถานะตามที่มีอยู่แล้วในแอป: ✅ ผ่านด่านคณิตศาสตร์ (ไม่ต้องตรวจ) · ⚠️ ต้องเทียบรูปครอปด้วยตา (โชว์รูปข้างช่อง) · ❌ พิมพ์เอง — **ห้ามมีเลข % ความมั่นใจโผล่ที่ไหนเลย**
3. หน้าค้นลูกค้าเก่าต้องเด่นกว่าปุ่มถ่ายรูป — เจอในคลังแล้วดึงข้อมูลอัตโนมัติ ไม่ชวนถ่ายรูปซ้ำ (คือทางที่ทำให้ AI call เหลือ 0)
4. การ์ดอัพสลิปต้องรองรับ 2 ทาง: จับคู่ยอดตรงพอดี (badge เขียว "จับคู่อัตโนมัติ" + แตะรับทราบ) กับไม่ตรง (การ์ดให้เลือกก้อนค้าง + ป้ายเตือนเหลือง ไม่ใช่กำแพงบล็อก)
5. ทุกช่องที่ AI กรอกให้ ต้องแก้ทับด้วยมือได้เสมอ ไม่มีช่องไหนล็อกเฉพาะ AI แตะได้
