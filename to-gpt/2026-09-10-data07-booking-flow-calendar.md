## ⚠️ 0) แก้ของที่ผมเขียนผิดในก้อนที่ 2 — อ่านตรงนี้ก่อน

**ที่เขียนไว้ (ผิด)**: *"`returned` (58) กับ `completed` (5) เป็นคนละสถานะ และ `returned` คือเส้นทางหลักจริง — ปุ่มบนจอต้องแยกสองอันนี้"*

**ของจริงที่ตรวจกับโค้ดแล้ว**:
- ปุ่มปิดงานคืนรถในแอปปัจจุบัน (`action: "complete_return"`) เขียน **`status='completed'` เสมอ** — ไม่เคยเขียน `returned`
- `returned` **ไม่อยู่ในรายการสถานะที่ API ยอมให้ตั้งด้วยซ้ำ** (รับแค่ `pending` `confirmed` `active` `completed` `cancelled` `rejected`)
- แปลว่า **`returned` 58 ใบเป็นข้อมูลที่ import มาจากระบบเดิม** ไม่ใช่เส้นทางที่แอปสร้างใหม่

**สรุปที่ถูก**: ทั้งสองถือว่า "ปิดแล้ว" เท่ากัน (`closedBookingStatuses = ["completed","returned"]`)
→ จอมือถือ **ไม่ต้องมีสองปุ่ม** · มีปุ่มปิดงานเดียวที่ให้ผลเป็น `completed`
→ แต่ **ต้องอ่าน `returned` เป็น "ปิดแล้ว" ได้ด้วย** ไม่งั้นใบเก่า 58 ใบจะหลุดจากทุกจอสรุป
ขออภัยที่ส่งของผิดไปในก้อน 2 — ตัวเลข 58/5 ถูก แต่ข้อสรุปว่า "returned คือเส้นทางหลัก" ผิด

## 1) สถานะใบจอง — 6 ค่า และใครเปลี่ยนได้ยังไง

| สถานะ | ในฐานตอนนี้ | เกิดจาก | ปิดแล้วหรือยัง |
|---|---|---|---|
| `pending` | 21 | สร้างใบใหม่ (ค่าเริ่มต้น) | ❌ |
| `confirmed` | 16 | ทีมเปลี่ยนสถานะเอง | ❌ |
| `active` | 8 | **ปุ่ม "ปล่อยรถ" เท่านั้น** | ❌ |
| `completed` | 5 | **ปุ่ม "ปิดงานคืนรถ" เท่านั้น** | ✅ |
| `returned` | 58 | ข้อมูล import จากระบบเดิม | ✅ |
| `cancelled` | 1 | ปุ่มยกเลิก (ต้องมีเหตุผล) | — (ตัดออกจากทุกยอด) |
| `rejected` | 0 | — | — (ตัดออกจากทุกยอด) |

### กติกาการเปลี่ยนสถานะที่ API บังคับไว้
1. **`active` ตั้งตรง ๆ ไม่ได้** → `"กรุณาใช้ปุ่มปล่อยรถ ระบบจะตรวจการยืนยันก่อน"`
   ต้องผ่าน `action: "release_vehicle"` ซึ่งตั้ง `status='active'` + `pickup_done=1` + `released_at`
2. **ปิดงานคืนรถต้องผ่าน `action: "complete_return"`** → `completed` + `dropoff_done=1` + `deposit_returned` + `deposit_closed_at` + `refund_completed_at`
   · ใบที่ปิดแล้วกดซ้ำ → ปฏิเสธ `"รายการนี้ปิดงานคืนรถแล้ว"`
3. **ยกเลิก** (`action: "cancel_booking"`) ต้องมีเหตุผลเสมอ (ไม่มี → 400) และ:
   · ใบ `active` **ยกเลิกไม่ได้** → 409 `"รถถูกปล่อยแล้ว กรุณาคืนรถและปิดงานแทนการยกเลิก"`
   · ใบที่ปิด/ยกเลิกแล้ว → 409
   · ยกเลิกแล้วระบบทำ 5 อย่างเป็นก้อนเดียว: เปลี่ยนสถานะ + ต่อท้าย notes ว่ายกเลิกเมื่อไรเพราะอะไร + ทำใบยืนยันลูกค้าเป็นโมฆะ (`booking_confirmations.invalidated_at`) + ปิดร่าง LINE + แจ้งเตือน + `audit_log`

### 🔴 กติกาเหล็กที่ค้นเจอในซอร์ส — เขียนเงิน+audit ต้องเป็นก้อนเดียว
คอมเมนต์ในโค้ด `complete_return` เขียนไว้ตรง ๆ:
> *ต้องเขียนใบจอง+ธุรกรรม+audit เป็นก้อนเดียว (batch) ห้ามแยก audit ออก — เหตุผลเดียวกับบั๊กที่เจอในจอ `/jobs` 8 ก.ย. 69: ถ้าแยกกัน เงินจะถูกเขียนไปแล้วแต่หน้าจอบอกว่าล้มเหลว ทีมเห็น error แล้วกดซ้ำ*

→ **สำคัญกับคำถาม recovery/timeout ที่ G ถามมา**: ฝั่งเรา**เขียนแบบ all-or-nothing แล้ว**
ใบจอง · ยอดหักจากประกัน · ค่าใช้จ่ายตอนคืนรถ · แจ้งเตือน · audit — ทั้งหมดอยู่ใน `env.DB.batch()` เดียว
→ แต่ยัง **ไม่มี idempotency key** — ยิงซ้ำหลังเน็ตหลุดจะโดนด่านสถานะ (`"ปิดงานคืนรถแล้ว"`) ซึ่งกันได้จริงในทางปฏิบัติ แต่ไม่ใช่การรับประกันระดับ protocol

## 2) การกันจองชนคิว — 409 ที่ G ต้องออกแบบรองรับ

**`POST /api/bookings` ตรวจแบบนี้ ก่อนบันทึกเสมอ:**
```sql
SELECT id FROM bookings
WHERE car_id = ?
  AND status NOT IN ('cancelled','rejected')
  AND start_at < :endAt AND end_at > :startAt
LIMIT 1
```
เจอ → `409` + `"รถมีคิวซ้อนในช่วงที่เลือก กรุณาเลือกคันหรือวันใหม่"`

**สามเรื่องที่ต้องรู้**
1. **ตรวจถึงระดับนาที** (`start_at`/`end_at` เป็น epoch ms) ไม่ใช่ระดับวัน — ปฏิทินบนจอเป็นแค่ตัวช่วยเลือก
2. **`pending` ก็ล็อกคิว** — ใบที่ยังไม่ยืนยันกันคันไว้แล้ว
   🔴 เกี่ยวโดยตรงกับรูที่ยังไม่ปิด: `POST /api/bookings` **ยังไม่มีการ์ดสิทธิ์** → คนไม่ล็อกอินสร้างใบ `pending` ล็อกรถได้
   (โค้ดแก้+เทสต์พร้อมแล้วใน worktree รอเจ้าของสั่ง — G เคยได้รับแจ้งเรื่องนี้ในรอบ QC)
3. **409 อีกตัวที่ไม่เกี่ยวกับคิวรถ**: ร่างจาก LINE ที่ถูกแปลงเป็นใบจองไปแล้ว → `"ร่างจาก LINE นี้ถูกบันทึกเป็น Booking แล้ว"`
   → จอที่มาจากร่าง LINE ต้องแยกสอง 409 นี้ออกจากกัน (ตัวแรกให้เลือกคันใหม่ · ตัวหลังให้ปิดร่างทิ้ง)

## 4) ปฏิทินวันว่าง — 3 สถานะ ไม่ใช่ 2 (`lib/car-availability.ts`)

```
free    = ไม่มีใบจองคาบวันนี้เลย
partial = มีใบคาบบางช่วง → ยังเป็น "วันรับ" หรือ "วันคืน" ได้
busy    = มีใบกินทั้งวัน (startAt ≤ ต้นวัน และ endAt ≥ ปลายวัน) → ห้ามเลือก
```

**ทำไมต้องมี `partial`**: วันคืนรถของใบหนึ่งกับวันรับรถของอีกใบ **เป็นวันเดียวกันได้จริง** (คืนเช้า–ส่งต่อบ่าย)
- ตีว่า "มีใบคาบ = จองแล้ว" ทั้งหมด → ปฏิทินบอกไม่ว่างทั้งที่รับรถได้
- ตีว่าว่างหมด → ปล่อยให้เลือกช่วงที่รถอยู่กับคนอื่น

**`rangeIsBookable(start, end, windows)`** รวมกติกา 2 ชั้น:
1. วันคั่นกลางต้อง `free` สนิท (`firstBlockedDayInRange` — ตรวจเฉพาะวันคั่น ไม่รวมวันหัวท้าย)
2. วันรับกับวันคืนห้าม `busy` แต่ **`partial` ผ่านได้**

⚠️ **ทุกวันนับตามเวลาไทย** (`bangkokDayStartMs` = `T00:00:00+07:00`) ไม่ใช่ UTC
⚠️ **`monthGrid()` เริ่มสัปดาห์วันจันทร์** (`(getUTCDay() + 6) % 7`) — ไม่ใช่วันอาทิตย์
⚠️ **ค่านี้ใช้ "ช่วยเลือก" เท่านั้น** ตัวตัดสินจริงคือการตรวจคิวระดับนาทีตอนบันทึก
→ หน้าลูกค้าต้องเขียนกำกับเสมอว่าทีมจะยืนยันเวลาจริงอีกครั้ง **ห้ามเขียนว่า "จองได้เลย"**
