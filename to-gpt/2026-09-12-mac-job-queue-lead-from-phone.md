# กดบนมือถือ → เครื่อง Mac ยิงลีดให้ — ท่อที่ต้องสร้าง (12 ก.ย. 2569 · จาก C)

ตอบคำถามเจ้าของ: **"จะทำยังไงให้เพิ่มยิงจาก Mac ได้ โดยผ่านมือถือกดเพิ่มแชทใหม่"**

ปลดล็อกหัวข้อ **ช. "เฟซบุ๊กเข้ากล่องเดียวกัน"** ที่ค้างมาตั้งแต่ 8 ก.ย. (`2026-09-08-proposal-one-inbox-ai-secretary.md:141`)
และการ์ด `lead` ที่ GPT ติดป้าย "รอหลังบ้าน" ไว้ (`from-gpt/2026-09-08-assemble-next.md:91` · `2026-09-09-chat-inbox-assembled.md:18`)

**สถานะทั้งไฟล์นี้ = `proposed`** — ยังไม่มีอะไรในนี้อยู่จริงสักบรรทัด ไม่มี route ไม่มีตาราง ไม่มีตัวประจำเครื่อง
**ไม่มี token/secret/ข้อมูลลูกค้าในไฟล์นี้**

---

## 0) คำตอบสั้น 3 บรรทัด

1. **ต้องกลับทิศการเชื่อมต่อ** — เซิร์ฟเวอร์ยิงเข้าเครื่อง Mac **ไม่ได้** ต้องให้ **Mac วิ่งมาถามเซิร์ฟเวอร์เอง** ว่า "มีงานให้ทำไหม"
2. มือถือไม่ได้สั่ง Mac ตรง ๆ — มือถือ**หย่อนใบสั่งงานลงกล่อง** บนเซิร์ฟเวอร์ แล้ว Mac มาหยิบไปทำ
3. ของที่ต้องสร้าง: **ตารางใหม่ 1 ตาราง + API 5 เส้น + โปรแกรมเล็ก ๆ 1 ตัวที่เปิดค้างบน Mac**

หลักการนี้ **ไม่ใช่ของใหม่ในบ้านเรา** — `ส่งเข้าแอป.py` บน Mac ยิง `POST /api/bookings` เข้ามาอยู่แล้ว (`02-rental-ops-existing.md:147`) ทิศทางเดียวกันเป๊ะ แค่คราวนี้ Mac วิ่งมาถามก่อนว่ามีงานไหม แทนที่จะรอคนนั่งหน้าเครื่อง

## 1) ทำไมทางที่นึกภาพกันตอนแรกทำไม่ได้ — ต้องเข้าใจก่อน ไม่งั้นออกแบบผิดทั้งจอ

ภาพที่คนส่วนใหญ่นึก คือ "กดบนมือถือ → เซิร์ฟเวอร์สั่ง Mac → Mac ยิง" **ขาที่สองทำไม่ได้** ด้วยเหตุผล 3 ข้อ:

| ข้อ | ของจริง |
|---|---|
| **ไม่มีที่อยู่ให้ยิงไปหา** | เครื่อง Mac อยู่หลังเราเตอร์ (NAT) ไม่มี IP สาธารณะ ไม่มีชื่อโดเมน — Cloudflare Worker `fetch()` ไปหาไม่ได้ ไม่มีเลขให้กด |
| **ต่อให้เปิดรูก็ไม่ควร** | เปิด port forward = เปิดประตูจากอินเทอร์เน็ตทั้งใบเข้าเครื่องที่มีสคริปต์แตะฐานลูกค้า + คลัง PDF สัญญา · IP บ้าน/ออฟฟิศเปลี่ยนเองเมื่อไหร่ก็ได้ ท่อขาดเงียบ ๆ |
| **เครื่องหลับ = คำขอตายคาที่** | ยิงตรงแล้วเครื่องไม่ตอบ คือ error ทันทีตรงหน้าคนกด — **เราเจอแผลนี้มาแล้วกับสัญญา**: *"ข้อจำกัด: ต้องเปิด Mac ถึงออกสัญญาได้"* (`02-rental-ops-existing.md:148`) |

**กล่องงานแก้ข้อสามให้ด้วยโดยอัตโนมัติ** — Mac ดับอยู่ งานไม่หาย มันนอนรอในกล่อง พอเปิดเครื่องมันหยิบไปทำต่อเอง
เปลี่ยนอาการจาก **"พัง"** เป็น **"ช้า"** ซึ่งเป็นคนละเรื่องกันสำหรับคนใช้งาน

## 2) ท่อที่เสนอ

```
 ┌─────────────────────────┐
 │ มือถือ — /chat กล่องเดียว │
 │  [+] แชทใหม่ → "ยิงลีด"   │
 └───────────┬─────────────┘
             │ POST /api/mac-jobs   (Bearer ของคนกด — ระบบเดิม)
             ▼
 ┌───────────────────────────────────────────────┐
 │ Rental Ops (Cloudflare Worker + D1) — กล่องงาน │
 │  ตาราง mac_jobs : queued → claimed → running   │
 │                    → done / failed             │
 │  cron ที่มีอยู่แล้ว: กวาดงานค้างกลับเข้าคิว        │
 └──────▲──────────────────────────┬─────────────┘
        │ ทุก 5 วิ: "มีงานไหม"         │ การ์ดอัปเดตสด
        │ POST /api/mac-jobs/claim   │ GET /api/mac-jobs
        │ (Mac เป็นฝ่ายวิ่งมา ◄── หัวใจ) ▼
 ┌──────┴──────────────────┐   ┌─────────────────┐
 │ ตัวประจำเครื่องบน Mac      │   │ การ์ดในกล่องเดียว │
 │ (launchd เปิดค้างตลอด)    │   │ รอ→กำลังยิง→เสร็จ │
 │   └─▶ สกิล "ยิงลีด"       │   └─────────────────┘
 │   └─▶ (ทีหลัง) "ทำสัญญา"  │
 └─────────────────────────┘
```

**เวลาที่คาดหวัง**: กดบนมือถือ → Mac เริ่มทำงานภายใน **≤ 5 วินาที** (เท่ารอบ poll) — งานแบบนี้ไม่ต้องการทันทีระดับมิลลิวินาที

## 3) ของที่ต้องสร้างทั้งหมด — 3 ก้อน

| ก้อน | อยู่ที่ไหน | ใหญ่แค่ไหน |
|---|---|---|
| ตาราง `mac_jobs` (+ `mac_agents`) | D1 | 1–2 ตาราง ไม่แตะตารางเดิมเลย |
| API 5 เส้น `/api/mac-jobs*` | Worker เดิม | route ใหม่ ไม่แก้ของเก่า |
| ตัวประจำเครื่อง (agent) | เครื่อง Mac | สคริปต์ลูปเดียว ~100 บรรทัด + launchd 1 ไฟล์ |

**ไม่ต้อง**: ไม่ต้องเปิด port · ไม่ต้องใช้ ngrok/tunnel · ไม่ต้องมี IP นิ่ง · ไม่ต้องแตะบอทเลขา LINE · ไม่ต้องย้ายสกิล "ยิงลีด" ไปไหน (มันยังอยู่บน Mac เหมือนเดิมทุกอย่าง)

## 4) ตาราง `mac_jobs` — กล่องงาน

```sql
CREATE TABLE mac_jobs (
  id               TEXT PRIMARY KEY,
  kind             TEXT NOT NULL,           -- 'ยิงลีด' | 'ทำสัญญา' | ...
  payload          TEXT NOT NULL,           -- JSON ใบสั่งงาน
  status           TEXT NOT NULL            -- queued|claimed|running|done|failed|cancelled
                     DEFAULT 'queued',
  idempotency_key  TEXT NOT NULL UNIQUE,    -- ◄── กันกดซ้ำ (ดูข้อ 7)
  thread_id        TEXT,                    -- ผูกกับเธรดใน /chat (ข้อ 10)

  created_by       TEXT NOT NULL,           -- user id คนกด
  created_at       TEXT NOT NULL,

  claimed_by       TEXT,                    -- ชื่อเครื่อง เช่น 'mac-mini-office'
  claimed_at       TEXT,
  heartbeat_at     TEXT,                    -- ◄── Mac เต้นทุก 20 วิระหว่างทำงาน
  attempts         INTEGER NOT NULL DEFAULT 0,

  progress_done    INTEGER,                 -- ยิงไปแล้วกี่ราย
  progress_total   INTEGER,                 -- จากทั้งหมดกี่ราย
  progress_text    TEXT,

  finished_at      TEXT,
  result           TEXT,                    -- JSON ผลงาน
  error            TEXT                     -- ข้อความไทย ถ้าล้ม
);

CREATE INDEX idx_mac_jobs_queue  ON mac_jobs(status, created_at);
CREATE INDEX idx_mac_jobs_thread ON mac_jobs(thread_id);
```

⚠️ **`idempotency_key` ต้องเป็นคอลัมน์ของตัวเอง UNIQUE และมีค่าจริงเสมอ — ห้ามยัดค่าหลอกลงคอลัมน์ที่มี FOREIGN KEY แล้วหวังให้มันกันซ้ำ**
นี่คือบทเรียนข้อ 6 ตรง ๆ (`02-rental-ops-existing.md`): *"ค่าหลอกในคอลัมน์ที่มี FOREIGN KEY ใช้ไม่ได้ (ตัวกันยิงซ้ำเคยพังเงียบด้วยเหตุนี้)"* — เราพังเพราะเรื่องนี้มาแล้วหนึ่งรอบ อย่าพังซ้ำ
ด้วยเหตุผลเดียวกัน **`claimed_by` เก็บเป็นข้อความชื่อเครื่องเฉย ๆ ไม่ผูก FK** กับอะไรทั้งนั้น

ตารางที่สอง (เล็กมาก) ไว้ตอบคำถาม "เครื่องเปิดอยู่ไหม" — จำเป็น ดูข้อ 10:
```sql
CREATE TABLE mac_agents (
  name          TEXT PRIMARY KEY,   -- 'mac-mini-office'
  last_seen_at  TEXT NOT NULL,      -- ทุกครั้งที่มัน poll แม้ไม่มีงานก็ประทับ
  version       TEXT
);
```

## 5) API 5 เส้น

### 5.1 `POST /api/mac-jobs` — มือถือหย่อนใบสั่งงาน
สิทธิ์: Bearer ของคนในทีม (ระบบเดิม) · ต้องมีสิทธิ์ระดับที่เจ้าของกำหนด (ดูข้อ 12)

```
ส่งเข้า  { kind: "ยิงลีด",
          idempotencyKey: "<uuid ที่มือถือสร้าง>",
          payload: { model: "DNA 3", from: "2569-09-12", to: "2569-09-15",
                     target: "<โพสต์/กลุ่มที่จะยิง>", message: "<ข้อความ>", maxSend: 10 } }

ได้กลับ  201 { ok:true, jobId, status:"queued", threadId,
               agent: { online: true, lastSeenSeconds: 3 } }
         200 { ok:true, jobId, status:"queued", duplicated:true }   ← ส่ง key ซ้ำ คืนใบเดิม ไม่สร้างใหม่
         409 { ok:false, error:"มีงานยิงลีดค้างอยู่แล้ว 1 ใบ รอให้เสร็จก่อน" }
```
409 พร้อมข้อความไทย — ตามกติกาเดิมที่ทุก error ธุรกิจตอบ 409 ไม่ใช่ 400/500 (`2026-09-09-backend-contract-answers.md` ข้อ 2)

**`agent.online` ต้องคืนมาในคำตอบนี้เสมอ** เพื่อให้จอบอกคนกดได้ทันทีว่างานจะวิ่งเลย หรือจะนอนรอเครื่องเปิด

### 5.2 `POST /api/mac-jobs/claim` — Mac มาขอรับงาน (เส้นที่ Mac เรียกทุก 5 วิ)
สิทธิ์: **token ของเครื่อง** ไม่ใช่ของคน (ดูข้อ 6)

```
ส่งเข้า  { agent: "mac-mini-office", kinds: ["ยิงลีด"], version: "1.0.0" }
ได้กลับ  200 { ok:true, job: { id, kind, payload } }     ← ได้งาน
         200 { ok:true, job: null }                      ← ไม่มีงาน (กรณีปกติ 99%)
```
**ทุกครั้งที่เรียก ไม่ว่าจะได้งานหรือไม่ ให้ `UPSERT mac_agents.last_seen_at = now`** — การ poll ทำหน้าที่เป็นสัญญาณชีพไปในตัว ไม่ต้องมีเส้น ping แยก

การหยิบงานต้องเป็น **คำสั่งเดียวที่ atomic** ห้ามอ่านก่อนแล้วค่อยเขียน:
```sql
UPDATE mac_jobs
   SET status='claimed', claimed_by=?1, claimed_at=?2,
       heartbeat_at=?2, attempts = attempts + 1
 WHERE id = ( SELECT id FROM mac_jobs
               WHERE status='queued' AND kind IN (...)
               ORDER BY created_at LIMIT 1 )
   AND status='queued'          -- ◄── ด่านกันสองเครื่องแย่งใบเดียวกัน
RETURNING id, kind, payload;
```
**แล้วต้องเช็ค `meta.changes === 1` เสมอ** — ถ้าได้ 0 แปลว่าไม่มีงาน หรือมีคนชิงไปแล้ว ให้ถือว่าไม่ได้งาน **ห้ามเดาว่าสำเร็จ** (บทเรียนข้อ 7: *"ไม่มีบันทึก ≠ ไม่ได้เกิดขึ้น"*)

### 5.3 `POST /api/mac-jobs/:id/progress` — รายงานสด + สัญญาณชีพ
```
ส่งเข้า  { done: 3, total: 10, text: "ทักอินบ็อกซ์ไปแล้ว 3 ราย" }
ได้กลับ  200 { ok:true }
         409 { ok:false, error:"งานนี้ถูกยกเลิกแล้ว หยุดทำงานทันที" }   ← ทางเดียวที่จะสั่ง Mac หยุดกลางคัน
```
ตั้ง `status='running'` + `heartbeat_at=now` · Mac เรียกทุก 20 วินาทีเป็นอย่างช้า แม้ไม่มีความคืบหน้าใหม่

### 5.4 `POST /api/mac-jobs/:id/result` — ปิดงาน
```
ส่งเข้า  { ok: true,  result: { sent: 10, replied: 2, leads: [ {name, model, note, at}, ... ] } }
   หรือ  { ok: false, error: "เข้าเฟซบุ๊กไม่ได้ — เซสชันหมดอายุ ต้องล็อกอินใหม่บนเครื่อง" }
ได้กลับ  200 { ok:true }
```
`error` ที่ส่งมา **ต้องขึ้นหน้าการ์ดคำต่อคำ** — ห้ามกลืนแล้วขึ้นว่า "ล้มเหลว" เฉย ๆ (บทเรียนข้อ 7: *"ระบบที่กลืน error ทุกด่าน debug ไม่ได้"*)

### 5.5 `GET /api/mac-jobs` — มือถือดูสถานะ
```
ได้กลับ  { ok:true,
           agent: { online:false, lastSeenSeconds: 7200 },
           jobs: [ { id, kind, status, progress:{done,total,text},
                     createdAt, finishedAt, result, error } ] }
```
คืนเฉพาะงานของทีมตัวเอง · PII ในผลลีด (ชื่อ/โปรไฟล์ลูกค้า) **ตัดที่ API ตามสิทธิ์ ไม่ใช่ซ่อนบนจอ** (บทเรียนข้อ 4)

## 6) ตัวตนของเครื่อง Mac — token ของเครื่อง ไม่ใช่ของคน

กติกาเดิมคือ *"ทุกคำขอต้องมี Bearer token ของผู้ใช้ ... ระบบไม่เชื่อ header อื่นเป็นตัวตน"* (`01-mobile-app-to-build.md:131`)
เครื่อง Mac ไม่ใช่คน ไม่มีอีเมล ไม่มีใครมานั่งกรอก OTP ให้ทุกเช้า → ต้องมี **บัญชีเครื่อง** เพิ่ม

| เรื่อง | ที่เสนอ |
|---|---|
| ชนิด | บัญชีชนิด `machine` แยกจาก `owner`/`staff` ในตารางสิทธิ์เดิม |
| สิทธิ์ | **แตะได้เฉพาะ `/api/mac-jobs/*` เท่านั้น** — อ่านลูกค้าไม่ได้ สร้างใบจองไม่ได้ ดูเงินไม่ได้ |
| เก็บที่ไหน | **macOS Keychain** (`security add-generic-password -s dnaev-mac-agent`) — ไม่อยู่ในไฟล์ ไม่อยู่ในรีโป ไม่อยู่ใน plist |
| อายุ | ยาว แต่ **เพิกถอนได้จากแท็บ `team`** — เครื่องหาย/ถูกขโมย กดตัดจากมือถือได้ทันที |

เหตุผลที่ต้องคุมสิทธิ์แคบ: token ตัวนี้นอนอยู่บนเครื่องเดสก์ท็อปตลอดเวลา ไม่ได้หมดอายุทุกวันแบบ OTP ของคน — ถ้ามันรั่ว ความเสียหายต้องจำกัดอยู่แค่ "แกล้งรับงานไปทิ้ง" ไม่ใช่ "ดูดฐานลูกค้าทั้งก้อน"

## 7) กันยิงซ้ำ 3 ชั้น

การยิงลีดซ้ำ = ทักลูกค้าคนเดิมสองครั้ง = เสียหายจริงกับหน้าร้าน ไม่ใช่แค่ข้อมูลเพี้ยน

| ชั้น | กันอะไร | ทำยังไง |
|---|---|---|
| 1. มือถือ | นิ้วลั่น กดปุ่มรัว | มือถือสร้าง `idempotencyKey` **ตอนเปิดฟอร์ม** (ไม่ใช่ตอนกดส่ง) ส่ง key เดิมทุกครั้ง → เส้น 5.1 คืนใบเดิม `duplicated:true` |
| 2. เซิร์ฟเวอร์ | สองเครื่อง / สอง tab แย่งงานใบเดียว | `UPDATE ... WHERE status='queued'` แล้วเช็ค `changes===1` (ข้อ 5.2) |
| 3. ตัวงานเอง | เน็ตหลุดตอนส่งผล → คิดว่าล้ม → ทำใหม่ | ฝั่ง Mac จดรายชื่อที่ยิงไปแล้วลงไฟล์ก่อนยิงจริง · ถ้า `attempts > 1` ให้ข้ามรายที่จดไว้แล้ว |

**`attempts` ต้องมีเพดาน** — เกิน 3 ครั้งให้ `status='failed'` พร้อม `error` ที่อ่านรู้เรื่อง ห้ามวนไม่จบ

## 8) เครื่องดับกลางคัน — งานต้องไม่ค้างเป็นผี

ถ้า Mac หยิบงานไปแล้วไฟดับ งานจะค้างที่ `running` ตลอดกาล ไม่มีใครมาปิดให้

ใช้ **cron ที่มีอยู่แล้ว** (`scheduled()` ของ Worker — ตัวเดียวกับที่ทำสรุปเช้า 07:00) เพิ่มงานกวาด:
```
ทุกรอบ: งานที่ status IN ('claimed','running') AND heartbeat_at < now-3นาที
  → attempts < 3 : คืนเป็น 'queued'  (เครื่องกลับมาก็ทำต่อ)
  → attempts >= 3: 'failed' + error "เครื่อง Mac ขาดการติดต่อกลางคัน 3 ครั้ง"
จดลง scheduled_run_log ทุกรอบเหมือนงาน cron อื่น
```
งานที่ `queued` เฉย ๆ **ห้ามหมดอายุเอง** — นั่นคือจุดขายของกล่อง: เปิดเครื่องเมื่อไหร่ก็ได้ทำ

## 9) ตัวประจำเครื่องบน Mac — 4 เรื่องที่พลาดแล้วเงียบ

| เรื่อง | ต้องทำ |
|---|---|
| **เปิดค้างเองตลอด** | `launchd` แบบ **LaunchAgent** (`~/Library/LaunchAgents/`) **ไม่ใช่ LaunchDaemon** — เพราะสกิล "ยิงลีด" ต้องใช้เซสชันผู้ใช้จริง (เบราว์เซอร์ + Keychain) · ตั้ง `RunAtLoad` + `KeepAlive` ให้มันฟื้นเองเมื่อตาย |
| **เครื่องต้องไม่หลับ** | macOS หลับ = หยุด poll = งานนอนในกล่องทั้งวันโดยไม่มีใครรู้ · ใช้ `caffeinate -s` ครอบ หรือ `sudo pmset -a sleep 0` · **เครื่องที่เหมาะคือ Mac mini เสียบไฟตลอด** — MacBook ปิดฝาแล้วหลับยังไงก็หลับ |
| **เน็ตหลุด** | poll ล้มต้อง retry แบบถอยหลัง (5→10→30→60 วิ) แล้วกลับมา 5 วิเมื่อต่อได้ · **ห้ามตายทิ้ง** |
| **จดทุกอย่าง** | เขียน log ลงไฟล์ในเครื่องทุกรอบที่หยิบงาน/ส่งผล — เวลามันเงียบจะได้รู้ว่าเงียบตรงไหน |

**ภาระที่ใส่เซิร์ฟเวอร์**: poll ทุก 5 วิ = 720 คำขอ/ชั่วโมง ≈ 8,600 คำขอ/วัน (ถ้าเปิดเครื่อง 12 ชม.) — เป็นคำขอที่เบามาก (SELECT เดียว) แต่ถ้าอยากประหยัด ให้ยืดเป็น 15 วิเมื่อไม่มีงานติดกันเกิน 5 นาที แล้วหดกลับ 5 วิหลังเพิ่งมีงาน

## 10) ฝั่งจอ — สิ่งที่ GPT ต้องออกแบบ

วันนี้ `/chat` เป็น **การ์ดอ่านอย่างเดียว** ช่องพิมพ์ล่างปิดใช้งานอยู่ (`2026-09-09-chat-inbox-assembled.md` ข้อ 4) — **ยังไม่มีปุ่ม "แชทใหม่" เลย** อันนี้จะเป็น **ทางเขียนทางแรกจากมือถือเข้าเครื่อง Mac**

**ก. ปุ่ม `[+] แชทใหม่`** → แผ่นเลือกชนิดงาน (รอบแรกมีตัวเดียวคือ "ยิงลีด") → ฟอร์มสั้น: รุ่นรถ · ช่วงวัน · เป้าหมาย · ข้อความ · จำนวนสูงสุด → ปุ่ม **[ยิง]**

**ข. ต้องบอกสถานะเครื่องก่อนกด ห้ามให้กดแบบไม่รู้อนาคต** — ใช้ `agent.online` จากข้อ 5.1/5.5:
- ออนไลน์ → *"เครื่อง Mac พร้อม — จะเริ่มยิงใน 5 วินาที"*
- ออฟไลน์ → *"เครื่อง Mac ปิดอยู่ (เห็นล่าสุด 2 ชม.ที่แล้ว) — งานจะรอในคิวจนเปิดเครื่อง"* ← **ยังกดได้** แต่ต้องรู้ตัว

**ค. หนึ่งงาน = หนึ่งเธรด** ตอบโจทย์ "กดเพิ่มแชทใหม่" ตรงตัว — ความคืบหน้าไหลเป็นข้อความในเธรดนั้น:
```
รอเครื่อง Mac …            (queued)
เครื่องรับงานแล้ว            (claimed)
กำลังยิง 3/10 …            (running — จาก progress)
ยิงแล้ว 10 · ตอบกลับ 2 ✅   (done)
เข้าเฟซบุ๊กไม่ได้ — เซสชัน
หมดอายุ ต้องล็อกอินใหม่ ⛔   (failed — error คำต่อคำ)
```

**ง. กติกาที่ห้ามแหก** (ของเดิมทั้งหมด):
- `queued` ที่ยังไม่มีผล ให้ขึ้น **"—"** ห้ามขึ้นเลขหลอกหรือแถบวิ่งปลอม (บทเรียนข้อ 3)
- 5 สถานะต้องแยกออกจากกันด้วยตาเปล่า **โดยไม่พึ่งสีอย่างเดียว** (กลางแดดคอนทราสต์ ≥ 7:1)
- ปุ่ม **[ยกเลิก]** ตอน `queued` = ลบออกจากคิวได้จริง · ตอน `running` = สั่งหยุดผ่านเส้น 5.3 (Mac รู้ตัวช้าสุด 20 วิ) → **ข้อความบนปุ่มต้องต่างกัน** ห้ามใช้คำเดียวกันสองความหมาย (แผลเดิมเรื่อง "ปิดจ๊อบ" สองความหมาย)

**จ. ขั้นที่ 2 — ลีดกลายเป็นใบจอง**: `result.leads[]` แต่ละราย ขึ้นเป็นการ์ด *"ลีดเฟซบุ๊ก: [ชื่อ] สนใจ [รุ่น]"* แตะแล้วกรอกต่อเป็นใบจองได้เลย — คือภาพที่หัวข้อ ช. วาดไว้เป๊ะ ๆ **ต้องมีตาราง `leads` ก่อน ยังไม่มี** (ดูข้อ 13)

## 11) ทางอื่นที่ดูแล้ว — และทำไมยังไม่เอา

| ทาง | ได้อะไร | ทำไมไม่เอาตอนนี้ |
|---|---|---|
| **Cloudflare Tunnel** (`cloudflared` บน Mac) | ทันที ไม่ต้อง poll | ยังต้องเลี้ยง daemon ให้ไม่ตายอยู่ดี · เครื่องหลับ = 502 คาหน้าคนกด ไม่มีคิวรองรับ · เพิ่มหน้าบ้านที่ต้องดูแล auth อีกชุด **แก้ปัญหาน้อยกว่าที่เพิ่ม** |
| **WebSocket ค้างไว้** (Durable Object) | ทันที ไม่ต้อง poll ไม่ต้องเปิด port | ต้องเพิ่ม Durable Object ซึ่ง**ยังไม่มีในสแตกเลย** (ตอนนี้ D1 ล้วน) + ต้องเขียน logic ต่อใหม่เมื่อหลุด — ของดี แต่ไว้ตอนที่ 5 วินาทีเริ่มรำคาญจริง |
| **APNs ปลุกมือถือ** | — | คนละทิศ ปัญหาเราคือปลุก **Mac** ไม่ใช่ปลุกมือถือ · และการ์ดทีมยังไม่มี APNs อยู่แล้ว |

**ถ้าจะย้ายทีหลัง กล่องงานไม่เสียของ** — ตาราง `mac_jobs` ยังเป็นสมุดบันทึกความจริงเหมือนเดิม เปลี่ยนแค่วิธีปลุก Mac จาก "ถามทุก 5 วิ" เป็น "ถูกเคาะ" เส้น API อื่นไม่ต้องแก้สักเส้น

## 12) ต้องให้เจ้าของเคาะ 4 ข้อ — ออกแบบไปก่อนได้ ติดป้ายไว้ ไม่ต้องหยุดรอ

1. **ใครกดยิงลีดได้** — เจ้าของคนเดียว หรือ staff ด้วย? (ยิงพลาด = หน้าร้านเสีย ไม่ใช่แค่ข้อมูลเพี้ยน) → **ค่าเริ่มต้นที่ผมจะใช้ถ้าไม่มีคำสั่ง: เจ้าของเท่านั้น**
2. **เครื่องไหนเป็นเครื่องประจำ** — Mac mini เสียบไฟตลอดคือคำตอบที่ถูก ถ้าเป็น MacBook ที่หิ้วกลับบ้าน กล่องงานจะทำงานเป็นช่วง ๆ ตามเวลาที่เปิดฝา ซึ่งก็ยังใช้ได้ แค่ต้องรู้
3. **เพดานการยิงต่อวัน** — ควรฝังเพดานไว้ในกล่อง (เช่น ไม่เกิน N รายต่อชั่วโมง) ให้เซิร์ฟเวอร์ปฏิเสธเองตั้งแต่ข้อ 5.1 ดีกว่าไปพึ่งวินัยคนกด
4. **ความเสี่ยงฝั่งเฟซบุ๊ก (ต้องพูดตรง ๆ)** — การทักอินบ็อกซ์อัตโนมัติจากบัญชีบุคคล ผิดเงื่อนไขการใช้งานของเฟซบุ๊ก และบทลงโทษคือ**ล็อกบัญชี/เพจ** ไม่ใช่แค่เตือน · ท่อนี้**ไม่ได้เพิ่มความเสี่ยง**เพราะพี่ยิงอยู่แล้วบน Mac แต่มัน**ทำให้ยิงง่ายขึ้นมาก** จึงมีโอกาสยิงถี่ขึ้นโดยไม่ตั้งใจ → เพดานข้อ 3 ไม่ใช่ของประดับ · ทางที่ปลอดภัยกว่าระยะยาวคือ **Messenger API ของเพจธุรกิจ** (ถูกกติกา มี webhook จริง เข้ากล่องเดียวได้โดยไม่ต้องพึ่ง Mac เลย) — เป็นคนละงาน ใหญ่กว่า ขอแยกออกไปก่อน

## 13) ทำเป็น 3 ขั้น — ขั้นแรกใช้ได้จริงแล้ว

| ขั้น | ได้อะไร | ของที่ต้องสร้าง |
|---|---|---|
| **1** | กดบนมือถือ → Mac ยิง → เห็นผลเป็นข้อความในเธรด | `mac_jobs` + `mac_agents` · API 5 เส้น · agent บน Mac · ปุ่ม `[+]` + การ์ด 5 สถานะ |
| **2** | ลีดแต่ละรายขึ้นเป็นการ์ด แตะแล้วกรอกต่อเป็นใบจอง | ตาราง `leads` + `GET /api/leads` + การ์ดลีด (ปิดหัวข้อ ช. ได้จริง) |
| **3** | "ทำสัญญา" ย้ายมาอยู่กล่องเดียวกัน | ใช้กล่องเดิมทั้งดุ้น เพิ่มแค่ `kind:'ทำสัญญา'` → **แก้แผล "ต้องเปิด Mac ถึงออกสัญญาได้" ได้ครึ่งทางทันที** (สั่งจากมือถือได้แล้ว แม้ยังต้องพึ่ง Mac ทำงาน) |

ขั้น 1 ไม่แตะโค้ดเดิมสักบรรทัด — ตารางใหม่ route ใหม่ล้วน ถ้าไม่เวิร์กก็ถอดทิ้งได้โดยไม่กระทบของที่ใช้งานอยู่
