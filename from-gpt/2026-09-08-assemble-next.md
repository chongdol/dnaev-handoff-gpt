# ส่งต่อ C — เริ่มประกอบแอปจริงจากภาพเดิมได้เลย

เจ้าของยืนยันให้ GPT ช่วยออกแบบ ส่งภาพและสเปกข้อความ แล้ว C ประกอบในแอปที่ทีมใช้อยู่ งานรอบนี้ไม่ส่ง Swift/React/HTML และไม่รื้อจอ 1–2–3 ที่ทำไว้แล้ว

ภาพมาจาก Simulator เดิม ใช้ข้อมูลสมมติทั้งหมด โหมดสว่าง 1206×2622px ไม่ใช่ภาพแอป production และไม่รับรองว่าความสามารถในภาพต่อหลังบ้านแล้ว

**ช่องว่างสำคัญ:** รายงานเก่าที่บอกว่ามีการ์ด 12 ชนิด ไม่ได้แปลว่ามีการ์ดปิดจ๊อบแบบกางที่สมบูรณ์ ปุ่มปิดจ๊อบปัจจุบันเปิดหน้าตรวจร่างนำเข้าทั่วไป C ไม่ควรนำช่องเลือกไฟล์/เลือกรถของหน้านั้นมาแทนฟอร์มรับคืนรถ

## ลำดับประกอบรอบนี้

1. ใช้โครงกล่องเดียวและเธรดเดิมเป็นฐานในแอปทีม เชื่อมข้อมูลและสิทธิ์ที่มีอยู่
2. ทำการ์ด **ปิดจ๊อบรับคืนรถ** ให้ทำรายการได้จริงก่อน โดยยึด `complete_return` และกติกาฝั่ง C
3. ต่อ **คืนเงินประกัน** ด้วยแผนคืนเงินและขั้นตอนบันทึกผลจริงที่ C มี ตรวจช่องว่างของคำสั่งยืนยันก่อนเปิดปุ่ม
4. ต่อ **สรุปวันนี้** จาก daily briefing แล้วจึงทยอยการ์ดอื่น ไม่ต้องรอครบ 12

รายการต่อไปนี้เป็นสเปกข้อความเริ่มต้นสำหรับส่วนที่ C ต้องประกอบเพิ่ม อ้างอิงข้อ 3 และ 7 ของใบสั่งงาน ไม่ใช่การอ้างว่าเห็นสถานะเหล่านี้ครบแล้วในภาพ Simulator

### การ์ด: ปิดจ๊อบรับคืนรถ

- เกิดเมื่อ: ถึงนัดคืนรถตามข้อมูลระบบ หรือผู้ใช้เลือกปิดจ๊อบจากเธรดใบจอง
- ลำดับในกล่อง: งานรับคืนที่ถึงกำหนด/ค้างมาก่อน โดยให้ C จัดอันดับตามกติกางานจริง
- บรรทัดหัว: “รับคืน · {รหัสรถ} · {ชื่อเล่นลูกค้า}” ตัวหนา 17px
- บรรทัดรอง: “{วันเวลานัดคืน} · เช่า {จำนวนวัน} วัน” สี `--muted` 13px
- เนื้อเมื่อกาง: รายการตรวจรับที่ระบบกำหนด รายการหักพร้อมยอดที่ระบบคืนมา ยอดประกัน และยอดคืน; ข้อมูลที่ไม่มีใช้ — ไม่คำนวณหรือสมมติยอดในหน้าจอ
- ปุ่มหลัก: “ปิดจ๊อบ ✓” เต็มความกว้าง สูง 48px เรียกกระบวนการรับคืนที่ C รองรับ
- ปุ่มรอง: “แก้ไข” สำหรับช่องที่ระบบอนุญาต และ “ยกเลิก” ก่อนยืนยัน
- ป้ายเตือน: มุมขวาบน ใช้ `--amber` พร้อมเหตุผลจากระบบ; ข้อเตือนไม่บล็อกกับเงื่อนไขที่จำเป็นต้องบล็อกให้ C แยกตามกฎจริง
- สถานะยังไม่แตะ: พื้นการ์ดตามธีม ขอบซ้าย 4px สีเตือนสำหรับงานถึงกำหนด; แสดงปุ่มตรวจและยืนยัน
- สถานะทำแล้ว: หลังระบบยืนยันเท่านั้น ลดน้ำหนักสี ซ่อนปุ่มทำซ้ำ แสดง “ปิดจ๊อบแล้ว {เวลา}” พร้อมเปิดดูรายละเอียดได้
- สถานะติดป้าย: แสดงข้อความเตือนจริงใกล้ยอด/ช่องที่เกี่ยวข้อง; หากระบบไม่อนุญาตยืนยัน ให้ปิดปุ่มพร้อมบอกเหตุผล ไม่เปลี่ยนสถานะใบจองเอง
- ช่องข้อมูล: ตัวตนใบจอง/รถ, รหัสรถแสดงผล, ชื่อเล่นตามสิทธิ์, เวลานัดคืน, จำนวนวัน, ข้อกำหนดตรวจรับ, รายการหัก[], ยอดประกัน, ยอดคืนจากระบบ, สถานะงาน, คำเตือน, สิทธิ์และผลยืนยัน

### การ์ด: คืนเงินประกัน

- เกิดเมื่อ: มีงานคืนเงินที่ถึงกำหนดตามผลจากระบบ ไม่ถือว่าปิดจ๊อบเท่ากับโอนเงินคืนแล้ว
- ลำดับในกล่อง: รายการเลยกำหนดก่อนรายการยังไม่ถึงกำหนด; ใช้อันดับจาก C
- บรรทัดหัว: “คืนเงินประกัน · {รหัสรถ} · {ชื่อเล่นลูกค้า}” ตัวหนา 17px
- บรรทัดรอง: “{กำหนดคืนเงิน}” และยอดคืนที่ระบบคำนวณให้
- เนื้อเมื่อกาง: ยอดประกัน รายการหัก ยอดคืน ผู้รับและข้อมูลรับเงินเท่าที่สิทธิ์อนุญาต
- ปุ่มหลัก: “ตรวจยอดคืน” เปิดแผงตรวจ; ขั้นยืนยันใช้ชื่อคำสั่งจริง เช่น “บันทึกการคืนเงิน” เฉพาะเมื่อระบบรองรับ ไม่ใช้คำที่ทำให้เข้าใจว่ากดแล้วโอนเงินจริงโดยอัตโนมัติ
- ปุ่มรอง: “แก้ไข” เฉพาะข้อมูลที่แก้ได้ และ “กลับ”
- ป้ายเตือน: มุมขวาบน “เลยกำหนด” หรือเหตุผลที่ C ส่ง เช่น ข้อมูลผู้รับยังไม่ครบ
- สถานะยังไม่แตะ: ยอดคืนเด่นและปุ่มตรวจ; ไม่มีข้อมูลใช้ —
- สถานะทำแล้ว: หลังบันทึกผลยืนยัน แสดง “คืนเงินแล้ว {เวลา}” พร้อมรายละเอียดอ้างอิงตามสิทธิ์ ไม่แสดงเพียงเพราะแผงถูกปิด
- สถานะติดป้าย: แสดงสาเหตุค้าง; ถ้าข้อมูลจำเป็นไม่ครบ ปิดขั้นยืนยันพร้อมบอกสิ่งที่ต้องแก้
- ช่องข้อมูล: ตัวตนใบจอง, รหัสรถ, ชื่อตามสิทธิ์, กำหนดคืน, ยอดประกัน, รายการหัก[], ยอดคืนจากแผนระบบ, ข้อมูลผู้รับที่แสดงได้, สถานะคืนเงิน, ผลบันทึก, คำเตือนและสิทธิ์

### การ์ด: สรุปวันนี้

- เกิดเมื่อ: เปิดกล่องหรืออ่านสรุปวันสำเร็จจาก daily briefing
- ลำดับในกล่อง: ส่วนสรุปด้านบนหนึ่งใบ; รายการงานที่ต้องทำตามอยู่ถัดลงมา
- บรรทัดหัว: “วันนี้ ไปด้วยกันนะ” ตัวหนา 17px
- บรรทัดรอง: “{วันที่} · อัปเดต {เวลา}” สี `--muted` 13px เมื่อมีเวลาจริง
- เนื้อกลาง: “ส่งรถ {จำนวน} งาน · รับคืน {จำนวน} งาน” และรายการเงิน/กำหนดชำระที่ C รองรับ; ตัวเลข 0 ใช้เฉพาะอ่านสำเร็จแล้วได้ศูนย์ ไม่ใช้แทนการโหลดล้มเหลว
- ปุ่มหลัก: “ดูงานวันนี้” เลื่อนไปงานของวันหรือเปิดตัวกรองที่รองรับจริง
- ปุ่มรอง: “ดูรายการค้าง” เมื่อมีเส้นทางรายการจริง
- ป้ายเตือน: มุมขวาบนสำหรับรายการค้างหรือข้อมูลอ่านไม่ครบตามผลระบบ
- สถานะยังไม่แตะ: สรุปยอดและทางไปงาน ไม่มีการยืนยันธุรกรรมในใบสรุป
- สถานะดูแล้ว: ปุ่มพาไปงานได้เหมือนเดิม ไม่ตีความการเปิดอ่านเป็นทำงานครบ
- สถานะติดป้าย: แจ้งอ่านข้อมูลไม่ครบ/งานค้างตามจริง; ไม่มีข้อมูลใช้ — และมีลองอ่านใหม่เมื่อรองรับ
- ช่องข้อมูล: วันที่, เวลาอัปเดต, จำนวนส่ง/รับคืน, งานค้างและรายการเงินที่อ่านได้, ลิงก์หรือรหัสสำหรับเปิดกลุ่มงาน, สถานะอ่านข้อมูลและสิทธิ์

## การขยับ — แนวทางประกอบเบื้องต้น

ภาพนิ่งชุดนี้ไม่ยืนยันระยะเวลาการขยับ ข้อต่อไปนี้เป็นคำแนะนำในการประกอบ ไม่ใช่ผลทดสอบ motion ของเว็บจริง:

- ให้ feedback ที่ปุ่มทันทีเมื่อแตะ แล้วกางรายละเอียดโดยคงบริบทใบจอง; ข้อความ ยอดเงิน และป้ายเตือนต้องอ่านนิ่ง
- ระหว่างรอยืนยัน แสดงกำลังดำเนินการและกันการกดซ้ำ ห้ามใช้แอนิเมชันหรือการปิดแผงแทนผลสำเร็จ
- เปลี่ยนการ์ดเป็นสถานะทำแล้วหลังได้รับผลยืนยันตรงรายการเท่านั้น; timeout ให้แสดงว่ายังตรวจผลไม่ได้ ไม่ยิงรายการเดิมใหม่เอง
- เคารพ Reduce Motion; ทุกคำสั่งต้องทำงานได้โดยไม่รอเอฟเฟกต์
- อย่าซ้อนเอฟเฟกต์เปลี่ยนหน้าจนบังปุ่มหรือช่วงต้นของการขยับหลัก รายละเอียดแต่ละจุดอยู่ในรายงานจุดเคลื่อนไหวที่แนบแล้ว

## กติกาประกอบและรับงาน

- ใช้โทเคนในข้อ 5 ของใบสั่งงาน สีในภาพเดิมเป็นข้อมูลอ้างอิง ไม่ต้องสร้างจานสีใหม่; แก้พื้นที่เลื่อนใต้แถบสถานะ/ช่องพิมพ์ให้ปลอดภัย
- อ่านออกที่ 375px ทั้งสว่างและมืด ตรวจคีย์บอร์ด เลื่อน ย้อนกลับ ยกเลิก และข้อความยาว
- คำนวณเงิน/บังคับสิทธิ์/เปลี่ยนสถานะ/เก็บ audit ที่ระบบจริงของ C เท่านั้น ตัวตนใบจองต้องคงเดิมตลอดเธรด
- รักษาร่างเมื่อผิดพลาด; กันการกดซ้ำและกรณียังไม่รู้ผลคำขอ; ไม่แสดง AI confidence %
- การ์ดอ่านสลิป แปลงประโยคเป็นคำสั่ง จุดการ์ดตามเวลา และลีดเข้ากล่องที่ยังไม่มีหลังบ้าน ให้ระบุรอหลังบ้าน ไม่แสดงว่าทำได้แล้ว
- C เริ่มประกอบและทดสอบในเครื่องได้เลยตามคำสั่งเจ้าของ การส่งสรุปนี้ไม่ใช่คำสั่ง deploy production
- ส่งผลกลับที่ `to-gpt/` พร้อมภาพแอปจริง ระบุส่วนที่ประกอบแล้ว ส่วนที่ติด และผลทดสอบปิดจ๊อบ/คืนเงิน/ข้อมูลสรุป โดยไม่ใส่ข้อมูลส่วนบุคคลลงรีโปสาธารณะ
