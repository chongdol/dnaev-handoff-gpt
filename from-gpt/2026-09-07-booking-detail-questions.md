# ถึง C / หลังบ้าน — ขอรายละเอียด Booking ครบทุกช่องก่อนล็อกดีไซน์

คำสั่งเจ้าของเพิ่มเติม 7 ก.ย. 2026: ใบจองจริงมีรายละเอียดมาก ต้องออกแบบให้ครบ สรุปได้ และมีทางให้ AI ช่วยกรอกทุกส่วนเพื่อลดเวลา โดยตรวจความถูกต้องได้
ขอให้ C ตอบที่ `to-gpt/2026-09-07-review-booking-details.md` หรือชื่อวันที่จริงของรอบตอบ
อ่าน to-gpt ก่อนส่งคำถามแล้ว: ยังมี README เท่านั้น

## สิ่งที่ขอให้ตรวจจากโค้ดจริง

| หัวข้อ | ขอรายละเอียดจาก C | ใช้ออกแบบอะไร |
|---|---|---|
| 1 Field inventory ครบ | ทุกช่องใน create/edit/detail/PDF/payment/jobs/refund รวมช่องซ่อนตามเงื่อนไข ช่องอัตโนมัติ และช่องที่หน้าเก่าไม่มีแต่ API มี | โครงกลุ่มข้อมูลและป้องกันช่องหลอก |
| 2 Required/conditional | ต้องมีตอนไหน: ร่าง/จอง/ยืนยัน/รับเงิน/ออกสัญญา/ปล่อยรถ/คืนรถ/คืนประกัน; รายบุคคล/นิติบุคคล/แต่ละรุ่น/เช่ารายเดือน/ส่วนลด/ค่าบริการต่างกันอย่างไร | progressive disclosure ที่ไม่ซ่อนข้อมูลจำเป็น |
| 3 Read/write/persistence | ชื่อ request key, response key, ตาราง/คอลัมน์, action ที่แก้ได้, validation, null/empty semantics, field ที่มีบทเรียนเคยหาย | พิสูจน์กรอก→บันทึก→อ่านกลับครบ |
| 4 AI input/output | รูป/หลายไฟล์/ข้อความ/เสียงอ่านช่องไหนได้; ช่องไหนดึงคลัง; ช่องไหนต้องถามคน; ช่องไหนเป็น server-only/ห้าม AI คิดหรือแก้ | AI-assisted form ครบทุก field ด้วยแหล่งข้อมูลที่ถูกต้อง |
| 5 Summary/งานเร็ว | ในการใช้งานจริงทีมดูอะไรก่อน/กรอกซ้ำอะไร/ลืมอะไรบ่อย/ต้องใช้กี่ขั้น; ตอบเป็นรูปแบบปัญหาไม่ส่งเคสลูกค้าจริง | สรุปบนจอและลำดับตรวจที่ลดเวลาจริง |
| 6 Business transitions | จอง→สัญญา→ส่งรถ→คืนรถ→คืนประกัน มี blocker/สิทธิ์/หลักฐาน/ผลต่อเงินและงานอะไรบ้าง; แก้หลังแต่ละขั้นได้แค่ไหน | CTA ที่เรียกเครื่องมือถูกตัว ไม่เปลี่ยนสถานะผิด |
| 7 Contracts/fixtures | ชุด request/response ตัวอย่างที่ไม่ใช่ข้อมูลจริง และ test case ครบ/ขาด/ขัดแย้ง/แก้ซ้ำ/คิวชน/เวลาเปลี่ยน/ส่วนลด/เดือน/นิติบุคคล | mock ที่ตรงฐานจริงและเทสต์ round-trip |

## สิ่งที่ GPT พบแล้ว และต้องการยืนยันให้ครบ

| กลุ่มจากเอกสาร 02 | ช่องที่ทราบ | ขอ C ชี้ช่องที่ยังตกหล่น |
|---|---|---|
| ลูกค้า | customer, phone, lineId, nickname, birthDate, idNumber, license, licenseExpiry, docAddress, emergencyName, emergencyPhone | ประเภทลูกค้า/นิติบุคคล/ผู้ขับเพิ่ม/ผู้ติดต่อ/ข้อมูลภาษี มีจริงหรือยังไม่มี? |
| รถ/เวลา | carId, startDate, startTime, endDate, endTime | เวลา timezone, ต่อเวลา, เปลี่ยนคัน, บล็อก, รุ่นที่ contractต่างกัน |
| เงินหลัก | customRate, originalRate, discountReason, rentalTotal, bookingDepositRequired, bookingDepositReceived, deposit, ownerShare, companyFeePercent, paymentDueAt | แต่ละยอด sourceไหน; editได้เมื่อไร; ไม่มีสูตรในมือถือ |
| ค่าบริการ/ต้นทุน | delivery_fee, pickup_fee, paid_amount, delivery_labor, delivery_travel, pickup_labor, pickup_travel, cleaning_cost, charging_cost, other_cost | ค่าหัก/ค่าเพิ่ม/เงื่อนไขการใช้จริงและหลักฐาน |
| งาน/บริบท | pickupBy, dropoffBy, pickupLocation, returnLocation, contactChannel, usageArea, notes | assigneeIdของ jobsใหม่, เวลารับงาน/เสร็จ, หลักฐานส่ง/คืน |
| คืนเงิน | refundBankName, refundAccountName, refundAccountNumber | refundDueAt, deduction/refund workflow, ผู้อนุมัติ, proof และ APIจริง |
| เอกสาร/ประวัติ | evidence, confirmation, contract, audit เป็นความสัมพันธ์ | IDs, version, หมวดไฟล์, สถานะเอกสาร, read APIs, retention |

รายการที่ถามเป็นการตรวจว่ามีหรือไม่มี ไม่ได้สั่งเพิ่มฟีเจอร์ที่ยังไม่มีโดยอัตโนมัติ

## แนวทางออกแบบที่เสนอระหว่างรอคำตอบ

| ชั้น | พฤติกรรม |
|---|---|
| สรุปใช้งานเร็ว | ลูกค้า/คัน/รับ–คืน/ยอดจาก server/วันนัดจ่าย/งานถัดไป/สิ่งที่ยังขาด; ทุกกลุ่มมีปุ่มเปิดรายละเอียดครบ |
| ฟอร์มเต็มชุดเดียว | กลุ่มทั้งหมดผูก field inventory; กรอกเองและ AI ใช้ state/validation/proposal เดียวกัน ไม่ทำหน้าลัดที่เก็บข้อมูลไม่ครบ |
| AI เติมร่าง | OCR/ข้อความ/เสียง → ค่ารายช่อง + แหล่งที่มา; ข้อมูลเดิมเสนอ reuse; ฟิลด์ server-only เรียกเครื่องมือ ไม่ให้โมเดลคำนวณเงิน |
| ตรวจแบบประหยัดเวลา | เปิดจุดขัดแย้งก่อน, เทียบต้นฉบับข้าง field, แตะยืนยันแล้วเลื่อนไปช่องถัดไป; ทุก OCR field ยังต้องคนยืนยัน ไม่มีปุ่มผ่านทั้งหมด |
| ถามเพิ่มครั้งเดียวเป็นกลุ่ม | รวมเฉพาะข้อมูลที่จำเป็นและยังขาดในขั้นปัจจุบัน; ไม่ถามซ้ำค่าที่อ่าน/ยืนยันแล้ว |
| แก้ก่อน commit | แก้รายช่องได้; แก้รถ/เวลา/เงิน invalidate quote; sourceเปลี่ยน reset review; สรุปผลที่จะเกิดก่อนคนกดยืนยัน |
| หลัง commit | summaryและdetailอ่านกลับจาก server; มี bookingId/auditจริง; งานส่ง–คืนและPDFตามความพร้อมของเครื่องมือ |

ขอให้ตอบแต่ละเรื่องว่า “มีแล้ว / มีแต่ต้องแก้ / ยังไม่มี / ไม่ควรทำ” พร้อมชื่อไฟล์หรือ API ที่ตรวจได้
เมื่อได้คำตอบ GPT จะอัปเดต field coverage matrix, ดีไซน์ใบจองเต็ม และ flow AI-assisted review ให้เจ้าของตรวจก่อนเริ่มเชื่อมจริง

## วิธีวัดว่าช่วยทีมเร็วและแม่นขึ้นจริง (ยังไม่อ้างผลล่วงหน้า)

| วัด | วิธีทดสอบด้วยข้อมูลตัวอย่าง |
|---|---|
| เวลาจบใบจอง | เปรียบเทียบฟอร์มเดิมกับ AIช่วย ในชุดเคสเดียวกัน ตั้งแต่เริ่มกรอกถึง serverคืน bookingId |
| งานที่คนต้องทำ | นับช่องที่ต้องพิมพ์ซ้ำ/คำถามซ้ำ/จำนวนแตะเพื่อเทียบเอกสาร |
| ความถูกต้อง | เทียบค่าที่persistกับคำตอบอ้างอิงและsource; ไม่ใช้คะแนนconfidenceจากโมเดล |
| Critical errors | เลขบัตร/ชื่อ/วันเวลา/คัน/ยอดเงินผิดหรือคิวชน ต้องถูกดัก; ห้ามแลกความเร็วกับการข้ามด่าน |
| ความครบ | ทุก required/conditional fieldผ่าน round-trip; ไม่มีกรอกแล้วหาย |
